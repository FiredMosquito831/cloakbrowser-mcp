# camoufox

Claude Code plugin fixed to the **Camoufox** contract engine: stealth Firefox driven by `camoufox-playwright-mcp==0.1.5` through the Playwright MCP tool contract. One MCP entry (`STEALTH_ENGINE=camoufox`), server key `camoufox`, tool names `mcp__plugin_camoufox_camoufox__*`.

The default `portable` profile exposes **27 tools**: the shared 24-tool `browser_*` core plus the three broker meta-tools (`browser_capabilities`, `browser_engine_status`, `browser_profiles`). `full` exposes **70**: 67 `browser_*` tools plus the three meta-tools. Five canonical tools are not exposed: `browser_annotate`, `browser_emulate_media`, `browser_start_recording` and `browser_stop_recording` are not implemented by the wrapper, and `browser_pdf_save` cannot run on Firefox. This engine has no CDP and no Cloak-specific diagnostics.

This plugin is the single-engine alternative to the universal `cloakbrowser` plugin. Install one path per engine, never both.

## Install

From the marketplace:

```
/plugin marketplace add FiredMosquito831/cloakbrowser-mcp
/plugin install camoufox@cloakbrowser-mcp
```

From a local checkout:

```
/plugin marketplace add D:\Projects2\StealthBrowserAutomation\fork
/plugin install camoufox@cloakbrowser-mcp
```

Claude Code prompts for the settings below during install. Non-interactively:

```bash
claude plugin install camoufox@cloakbrowser-mcp \
  --config headless=false \
  --config profile_dir=/home/you/.camoufox-profiles/linkedin
```

Change them later with `/plugin` → Configure, the per-option rows in `/config`, or:

```bash
claude plugin configure camoufox@cloakbrowser-mcp

printf '%s' '{"profile_dir":"/home/you/.camoufox-profiles/linkedin"}' | \
  claude plugin configure camoufox@cloakbrowser-mcp --values-stdin
```

Restart Claude Code after a change so the MCP server restarts with the new environment.

## Engine

The engine is fixed to `camoufox` in `.mcp.json`; there is no `browser_engine` setting and nothing to switch. `browser_capabilities.engineChoices` reports only `["camoufox"]`, `engineDefaultToolProfile` is `portable`, and `launch` is `launch-camoufox.mjs`. The engine set in this plugin is `engines/camoufox.json` plus the shared `engines/profiles.json`; the manifest is a generated copy of the universal plugin's canonical manifest.

`browser_capabilities.howToChangeEngine` is inherited from the shared broker and still names the universal plugin. It is the only place this plugin mentions it: switching engines means installing `cloakbrowser`; this plugin cannot do it.

## Requirements and first start

- Node 22.13+ or 24+ for the broker. Nothing else is a manual prerequisite.
- The launcher provisions everything under Claude Code's plugin data directory at the first MCP server start: a pinned checksum-verified `uv` 0.13.5, a uv-managed CPython 3.13.17, and a venv with `camoufox-playwright-mcp==0.1.5` plus its Camoufox dependency. Nothing is installed system-wide and no launcher starts a shell.
- **The venv pins the Python MCP stack.** Beside the wrapper it installs `fastmcp==3.4.7` and `mcp==1.29.0`, the versions the wrapper's own `uv.lock` resolves. The wrapper's `pyproject.toml` declares only `fastmcp>=3.4.2` with no upper bound, so an unpinned install resolves fastmcp 4.x; that major answers in the 2026-07-28 protocol era, where every request gets a new session id, and the wrapper keys its browser backend by that id. It then starts a new browser on every tool call, and the second launch fails on the profile the first browser still holds (`exitCode=0`, the error users saw on 2.9.0). The pins are part of the venv marker, so an existing venv rebuilds itself on the next start with no manual step; `CAMOUFOX_MCP_PACKAGE` still overrides the wrapper pin and the stack pins stay. The pin is revisited when upstream bounds `fastmcp` or keys its backend by a stable id.
- **A `uv` you provide must be 0.13.5 or newer.** The pinned `uv` is the one that installs the managed CPython 3.13.17; older versions fail with `No download found for request: cpython-3.13.17-windows-x86_64-none` and the launcher exits. A `uv` on `PATH` older than 0.13.5, or one that does not answer `--version`, is ignored with one log line and the pinned copy is provisioned instead. An explicit `UV`/`UV_BIN` older than 0.13.5 is refused with the version it reported, never silently replaced.
- The pinned Camoufox build `v156.0.1-beta.39` is a **~1.3 GB download and ~2.4 GB on disk** in Camoufox's machine-wide cache (`%LOCALAPPDATA%\camoufox` on Windows). It is downloaded when absent. The browser starts on the first browser tool call, not at `initialize`.
- A cold first start can take tens of seconds; if Claude Code's MCP startup timeout expires, restart Claude Code (`/reload-plugins`). The next start reuses what was provisioned and downloads nothing.
- **Windows shim.** The pinned wrapper installs a signal watchdog through anyio, which Windows does not implement; without a fix the server exits before answering `initialize`. `camoufox_entry.py` replaces only that receiver with an empty one (the broker owns shutdown on every platform) and then runs the unmodified wrapper. On other platforms the shim is not installed.
- **Camoufox cache side effect.** Camoufox stores builds in a machine-wide user cache and its installer makes the build it installs the active one. Installing this pin can move another Camoufox consumer on this machine to `v156.0.1-beta.39`. This plugin's launches stay pinned through `CAMOUFOX_EXECUTABLE_PATH` regardless of the active build.

Overrides are environment variables, not plugin settings:

| Variable | Effect |
|---|---|
| `UV`, `UV_BIN` | Use this `uv` instead of `PATH` or the pinned copy. It must be 0.13.5 or newer: a broken, older or unanswering value fails instead of falling back |
| `UV_PYTHON`, `PYTHON` | Use this interpreter instead of the managed CPython. `UV_PYTHON` wins |
| `CAMOUFOX_MCP_PACKAGE` | Override `camoufox-playwright-mcp==0.1.5`; the venv marker detects the change and rebuilds the venv. The pinned `fastmcp==3.4.7` and `mcp==1.29.0` stay |
| `CAMOUFOX_BROWSER_BUILD` | Override the pinned browser build |

Only the official uv release (SHA-256 verified against the checksums in `lib/provision.mjs`), the Python builds uv resolves, the package index, and the Camoufox release index are contacted. `uv python install` runs with `--no-bin --no-registry`, and `UV_PYTHON_INSTALL_DIR`, `UV_CACHE_DIR` and the venvs all live under the plugin data directory.

## Settings

| Setting | Default | What it does |
|---|---|---|
| Headless | `false` | Headed is measurably less detectable. Turn on only for a display-less server |
| Tool profile | `default` | `default` follows the engine manifest (`portable` for Camoufox). `portable` exposes the shared 24-tool browser core; `full` exposes everything this engine supports. The seven tool groups and `disabled_tools` still apply. Restart Claude Code after changing it |
| Tool groups | all on | Seven checkboxes: vision, pdf, devtools, storage, network, testing, config. `tools_pdf` is kept for cross-engine configuration; this engine never exposes `browser_pdf_save` |
| Disabled tools | empty | Comma-separated exposed names hidden from `tools/list` and rejected on call |
| Profile isolation | `shared` | `shared` keeps one profile per account for every Claude Code window, exactly as before. `workspace` derives one profile per project folder (`profiles/camoufox/ws-<hash>`) with a fresh login state, and moves to a numbered sibling if that profile is already in use. `isolated` uses no profile at all: nothing is created or locked, cookies, logins and storage are not saved, and nothing persists after the session; Profile directory, Account profile and the default-profile pointer are ignored and reported for that start. `copy` runs the session on a temporary copy of the profile that Profile directory, Account profile, the default-profile pointer or the engine default resolves; the base is locked for the session and never written, and the copy is discarded on a clean shutdown (a crashed session leaves it under `profiles/camoufox/.sessions`, listed by `browser_profiles` and removed only by `scripts/profile-copy.mjs --prune`). `copy-keep` does the same and keeps the changes: a clean close replaces the base with the session copy and retains the old base beside it as `<name>.previous-<timestamp>`, which is never deleted automatically and accumulates until you remove it; a crash performs no swap. `copy-keep` is refused when the base is outside the plugin data directory. `copy` and `copy-keep` do not combine with `workspace`. In `shared`, `workspace`, `copy` and `copy-keep`, Account profile and Profile directory win over the mode. See [Profile and sessions](#profile-and-sessions) |
| Device identity | `profile` | `profile` gives each persistent profile one generated device identity: the first launch draws a fingerprint for this computer's operating system, stores it in `<profile>/.camoufox-identity.json` and reuses it on every later launch, so a site that keeps cookies also sees the same device. Delete that file to draw a new identity on the next start; copies of the profile carry it, so delete it inside a copy to give the copy a different device. `random` restores the per-launch draw. An isolated start has no profile and always draws a new identity. See [Device identity](#device-identity) |
| Server heartbeat timeout | `0` | How long the backend waits for an answer to its own heartbeat ping, in milliseconds. `0` disables the wrapper's heartbeat (a ping every 3 s that closes the browser when an answer is more than 5 s late); a positive value re-enables it with that deadline. An explicit `PLAYWRIGHT_MCP_PING_TIMEOUT_MS` in the environment wins. Other engines send no server heartbeat and ignore it |
| Saved logins and autofill | `false` | When on, Firefox's own password manager is enabled for the profile: saved logins in `logins.db` can be autofilled into matching login forms and Firefox offers to save new ones. A deliberate security trade-off — a page and the model can read filled credentials and a prompt-injected page can steer the model to a login form; the store travels with a copied profile. Plain-HTTP autofill stays off. The pinned build disables the manager by enterprise policy, so enabling it creates a plugin-owned overlay of the build (hardlinks and junctions, only the two password values changed) and runs that executable; see [Saved logins and autofill](#saved-logins-and-autofill) |
| Account profile | empty → this plugin's default profile | One profile per account: `profiles/camoufox/<name>`, and `default` reaches the existing `profiles/camoufox/default`. Wins over Profile isolation; ignored when Profile directory is set. Restart after changing it. See [Accounts](#accounts) |
| Profile directory | empty → `<plugin data>/profiles/camoufox/default` | Explicit profile path; wins over Account profile and Profile isolation. Persistent cookies, logins and the device identity file. One directory per account |
| Proxy server / bypass | empty | Sticky proxy and hosts that skip it |
| Artifacts directory | empty | Where screenshots, traces and session files are written. Empty means `.playwright-mcp` inside the client's first usable `file://` root (the project folder Claude Code opened), or `<plugin data>/output/<engine>` when the client advertises no usable file root; `browser_capabilities.outputDir` reports the effective directory |
| Unrestricted file access | `false` | Removes Playwright's file-access allowlist for tool-chosen paths and unblocks `file://` navigation, so the model can read and write any file your operating-system user can. A deliberate security trade-off: a prompt-injected page could make the model read or overwrite private files. Leave it off unless you need a path outside the Artifacts directory and the client workspace root |

The launcher drops empty optional values before starting the server, so leaving a directory or proxy blank behaves as "not configured" rather than as an empty path.

`browser_capabilities` also explains a file-access refusal: `serverCwd` is the directory the MCP server runs in, `outputDir` is the effective artifact directory, and `clientRoots` is the MCP roots the client advertised (one read-only `roots/list` request with a 2 s bound, cached for the session; `clientRootsError` carries the reason when they could not be read). When `output_dir` is empty the broker chooses the artifact directory before the engine starts — `.playwright-mcp` inside the client's first usable `file://` root, or `<plugin data>/output/<engine>` when no usable file root is available — and passes it to the wrapper as `PLAYWRIGHT_MCP_OUTPUT_DIR`, so the roots request is made during the `initialize` handshake in that case and lazily on the first `browser_capabilities` call when the setting already fixed the directory. Unlike the Cloak bridge, this engine's Python server receives the client's roots, so its workspace root is the client's first root. `initialize.instructions` adds one sentence naming the artifact directory, which default was applied, and the `output_dir` setting.

**Unrestricted file access** (`allow_unrestricted_file_access`, default off) removes that allowlist for tool-chosen paths and unblocks `file://` navigation. When it is on, the model may read and write **any file your operating-system user can**, not only the two roots — including files outside the project. That is a deliberate security trade-off, not a convenience: a prompt-injected page could ask the model to read credentials or overwrite a private file, and the plugin cannot distinguish that from your own request. Leave it off unless a workflow needs a path outside the roots; when you can, set the Artifacts directory instead. The launcher passes `PLAYWRIGHT_MCP_ALLOW_UNRESTRICTED_FILE_ACCESS=true` to the engine only when the setting is on; when it is off or unset the variable is not passed, so the default configuration is unchanged.

### Saved logins and autofill

**Saved logins and autofill** (`password_manager`, default **off**) enables Firefox's own password manager for this engine. When it is on, saved logins in the profile's `logins.db` can be autofilled into matching login forms and Firefox will offer to save new logins. This is a deliberate security trade-off, not a convenience. Autofilled credentials can be read by the page's own scripts, by the model through `browser_snapshot` or `browser_evaluate`, and by a prompt-injected page that steers the model to a login form; the plugin cannot tell a legitimate login page from a phishing one. The store is encrypted with the profile's `key4.db`, which sits in the same profile and is not bound to your Windows account (no primary password is set by default), so anyone who obtains the profile — a copy, a backup, `profile_isolation=copy`/`copy-keep`, or `scripts/profile-copy.mjs` — can decrypt the saved passwords; saved logins raise what a stolen profile is worth. Autofill on plain HTTP stays off, and address/credit-card autofill and form history stay off. **The plugin never reads, logs or transmits `logins.db` or `key4.db`**: `passwordManagerStore` is the file's existence only, and no credential value is ever printed. This setting does **not** change the [never-automate-the-credential-form rule](#sign-in): it only lets Firefox's own manager fill a credential you already chose to store; the model never types, submits, recovers or handles 2FA or CAPTCHA.

The pinned Camoufox build locks the manager off with its own enterprise policy (`PasswordManagerEnabled: false`, `OfferToSaveLogins: false` in `distribution/policies.json`), launch prefs alone lose to that lock, and this Windows build has no readable per-user policy directory. Enabling the setting therefore creates **one plugin-owned overlay of the installed build** under Claude Code's plugin data directory at `<plugin data>/camoufox-overlay/<build directory>/`: a real `distribution/` copied from the build with only those two policy values set to true (every other policy — telemetry, updates, extension uninstall, search engines, the form-history and profile-import locks — is preserved), a **junction** for every other top-level directory, a **hardlink** for every top-level file on the same volume (copies of the top-level files — about 310 MB — only when the plugin data and the Camoufox cache are on different volumes, guarded by a free-space check; never the whole 2.4 GB build), and an `overlay.json` marker. The launcher runs the overlay's `camoufox.exe` through `CAMOUFOX_EXECUTABLE_PATH` and the entry point strips a user `browser.camoufoxOptions.executable_path` from this session's plugin-data config copy (the user's file is never edited), so that key cannot silently bypass the overlay. The first enable, and every build/policy/format change, is proved with one short headless browser start (the overlay temporarily carries a geolocation-permission policy; `denied` is the only success) and the final policy is written afterwards. Any failure — creation, junctions, free space, integrity, verification — runs the **stock build normally** and reports `blocked-by-overlay` with the reason; a `prompt` answer is cached for that build and policy, a timeout or error is retried on the next start, and a directory at the overlay path that this plugin did not write is never used, overwritten or removed (`blocked-by-existing-overlay`). The overlay is rebuilt when the build, its policy, the overlay format or the marker's manifest changes; the current and one previous build are kept; a tree a running browser still holds is left in place and reported. Turning the setting off removes this plugin's overlay and record. `browser_capabilities` and `browser_engine_status` report `passwordManagerEnabled`, `passwordManagerApplies`, `passwordManagerSource` (`overlay`, `prefs`, `default`, `not-applicable`, `native-unavailable`, `blocked-by-overlay`, `blocked-by-existing-overlay`, `blocked-config`, `blocked-by-build-policy`), `passwordManagerPolicyFile` and `passwordManagerOverlay` (only when the overlay is in use), `passwordManagerOverlayMode` (`hardlink` or `copy`), `passwordManagerStore` (`firefox-logins-db-present` or `missing`, existence only) and a note. A build that no longer locks the manager off is used unchanged with the same signon prefs and reports `prefs`. Off is the default and changes nothing: no overlay, no record, no pref, no capability key, and the pinned build's own policy stays in force.

## Accounts

One browser profile per account. Set **Account profile** to a name such as `alice`; the broker resolves it to a directory under Claude Code's plugin data directory and starts Camoufox with it. With Account profile, Profile directory, the default-profile pointer and Profile isolation at their defaults, nothing changes: the plugin uses `profiles/camoufox/default` exactly as before.

| Account / setting | Effective profile directory |
|---|---|
| empty, isolation `shared` | `<plugin data>/profiles/camoufox/default` |
| empty, isolation `workspace` | `<plugin data>/profiles/camoufox/ws-<sha256(cwd)[:7]>` |
| empty, isolation `copy` | the same base `shared` resolves (`profiles/camoufox/default`, or the pointer/profile_dir/account), **copied** to `profiles/camoufox/.sessions/<base>-<YYYYMMDD-HHMMSS>-<pid>`; the base is not written |
| empty, isolation `copy-keep` | the same base and the same session copy as `copy`; on a clean close the old base is renamed to `<base>.previous-<YYYYMMDD-HHMMSS>` (retained) and the session copy takes its place. A crash performs no swap |
| any, isolation `isolated` | **none** — no profile directory is created, locked or used |
| `default` | `<plugin data>/profiles/camoufox/default` — the profile you already have |
| `alice` | `<plugin data>/profiles/camoufox/alice` |
| default pointer set, nothing else | the pointer's name in `<plugin data>/profiles/camoufox/.default`; `default` means `profiles/camoufox/default`, any other name maps as an account |
| `profile_dir` set, isolation `shared`/`workspace`/`copy`/`copy-keep` | that path, unchanged (with `copy-keep` it must be inside the plugin data directory); Account profile, the default pointer and Profile isolation are ignored |

Precedence is **Profile isolation `isolated` → Profile directory → Account profile → Default profile pointer → Profile isolation `workspace` → engine default**. `isolated` overrides the profile settings instead of being overridden; the settings it made inert are reported as `profileIgnored`. `copy` and `copy-keep` resolve their base exactly like `shared` and do not combine with `workspace`; set Profile directory to a per-project path if you want a per-project copy.

- **Names:** 1–64 characters, starting with a letter or digit, then letters, digits, `.`, `_` or `-`. No trailing dot, no slash, no Windows device name (`CON`, `NUL`, `COM1`, …). An invalid name is a start-up error: no browser starts and `browser_engine_status.lastError` carries the exact reason. The name is validated before any path is built.
- **One account at a time.** The plugin configuration holds one value per key, so one plugin instance runs one account. Changing Account profile, Profile directory or the proxy takes effect when the MCP server restarts — restart Claude Code. There is no runtime account switch.
- **Visibility.** `browser_capabilities` reports `account`, `profileDir`, `profileSource` (`profile_dir`, `account`, `pointer`, `workspace`, `isolated`, `engine`, `default`), `defaultProfileDir`, `profileDefault`, `profileDefaultSource`, `profileDefaultPath` and, when the pointer is broken, `profileDefaultError`, plus `availableAccounts` (at most 100 names), `availableAccountCount`, `accountApplies`, `profileApplies`, `profileIsolation`, `profileIsolationSource`, `profileFallback` and `profileLock`; an engine that declares its own lock file also adds `engineProfileLock`. The device identity is reported as `identityMode`, `identityApplies`, `identitySource`, `identityFile`, `identityCreatedAt` and `identityNote` (see [Device identity](#device-identity)). `browser_engine_status` adds `account`, `profileDir`, `profileIsolation`, `profileApplies`, `profileFallback`, `profileLock` and the same identity keys. An **isolated** start adds `profileSource: "isolated"`, `profileDir: null`, `profileLock: null`, `profileIgnored` (the profile settings it ignored, with the value supplied), `profileIgnoredReason` and `profileIsolationNote`; `profileIsolationNote` says that the pointer and set-default do not affect this session. The `browser_profiles` meta-tool reports the same profile facts on demand and writes the default-profile pointer. The broker creates the account, pointer and workspace directories; it never copies, renames, moves or deletes a profile.
- **One profile per account, always.** Two identities in one profile overwrite each other's cookies. Windows is case-insensitive, so `Alice` and `alice` are the same directory.
- **Concurrency.** Camoufox locks a profile while a session uses it. With `shared`, a second session on the same directory is refused by the engine; the plugin's preflight now reports the owner and the fix before starting it. With `workspace`, different project folders get different profiles and run their own browsers (each has its own process). Two windows in the same project folder fall back to a numbered sibling profile, which is a **fresh login state**. The CloakBrowser free-tier one-session limit does **not** apply to this engine; there is no CloakBrowser binary here.
- See [Sign-in](#sign-in) for the manual, headed login each account needs.

### Per-account proxy file

A proxy can be sticky per account with a file beside the profile instead of the global **Proxy server** setting:

```
<plugin data>/profiles/camoufox/alice.proxy          beside profiles/camoufox/alice/
<plugin data>/profiles/camoufox/default.proxy        beside profiles/camoufox/default/
<plugin data>/profiles/camoufox/ws-0b0e194.proxy     beside a workspace profile
```

- **Proxy server set:** it wins, and one line in the MCP log says the file is ignored. **Proxy server empty:** the file is read for the active account, or beside the default profile when no account is set (only if the file exists). No file means a direct connection.
- The file is one line, no comments: `http://user:pass@host:port`, `https://…`, `socks4://…` or `socks5://…`. A missing scheme means `http://`. Percent-encode `@`, `:`, `/` inside credentials. The value is passed to the engine unchanged.
- A file that cannot be read, is not valid UTF-8, has more than one non-empty line, or does not parse as a proxy URL is a **start-up error**: the browser does not start and the error names the file, never its contents. A bad file never falls back to a silent direct connection.
- **The file is a credential in plaintext.** On POSIX run `chmod 600 <file>`; on Windows it inherits the user-profile ACL (the plugin does not change permissions). Keep it out of the repository, shared backups, PRs and screenshots; back it up like a password. The plugin only reads it, never writes it.
- The URL is never logged and never returned: `browser_capabilities` reports `proxySource` (`setting`, `account-file`, `none` or `error`) and `proxyConfigured` (boolean). Credential-bearing URLs in relayed backend log lines are masked as `scheme://***@host`.

### Backup, rename and delete (manual)

- **Backup:** close Claude Code (at least the browser), then copy the account directory and its `.proxy` file. A live profile contains lock files and can be copied inconsistently. The device identity file sits inside the directory; keeping it keeps the device. For a checked copy that skips locks and caches, use the copy tool below.
- **Rename:** close the browser, rename the directory and the `.proxy` file, change Account profile (or Profile directory), and restart. Nothing is migrated for you.
- **Delete:** close the browser, delete the directory and the `.proxy` file. Irreversible. There is no delete in the plugin.
- To switch accounts: `/plugin` → Configure → set Account profile → restart Claude Code.

### Copy a profile (safe copies)

A copy branches an existing profile under a new account name with the same cookies, logins, local storage and device identity file. Use it to experiment from a signed-in state, to keep a checked backup, or to start a second account from the same point. **A copy is not a new identity**: it presents the same device and the same sessions (delete `.camoufox-identity.json` inside the copy for a different device), so the one-account-per-profile rule still applies. It is not a way to move a session to a different account or to skip that account's sign-in.

1. **Close the browser first.** The profile lock exists while a browser uses the directory and a live profile is not safe to copy. The tool refuses a source whose bridge lock names a live process, and it also reads Firefox's own `<profile>/parent.lock` with the same rule as the broker, so a live Camoufox is refused cleanly instead of failing mid-tree. A stale lock (owner gone) is ignored and is not copied. An unreadable lock also refuses the copy.
2. Run the copy tool, from a checkout of this repository at the repository root:

   ```powershell
   node plugins/camoufox/scripts/profile-copy.mjs --engine camoufox --from default --to work2 `
     --data-dir "$env:USERPROFILE\.claude\plugins\data\camoufox-cloakbrowser-mcp"
   ```

   An installed plugin carries the same script at `<plugin root>/scripts/profile-copy.mjs`, for example
   `%USERPROFILE%\.claude\plugins\cache\cloakbrowser-mcp\camoufox\<version>\scripts\profile-copy.mjs`.
   This plugin ships only the `camoufox` engine, so `--engine camoufox` is required: the tool's default engine is `cloak`, which this plugin does not contain and therefore rejects. The tool uses the same account rule and `profiles/camoufox/<name>` layout as the broker:
   - `--data-dir <path>` names the plugin data root. In a Claude Code process it is `CLAUDE_PLUGIN_DATA`; a terminal normally does not have that variable, so pass the directory shown by `browser_capabilities.profileDir` two levels up — for this plugin `%USERPROFILE%\.claude\plugins\data\camoufox-cloakbrowser-mcp`. The fallback when nothing is set is `~/.cloakbrowser-mcp-plugin`, which is why the command above passes it explicitly.
   - `--dry-run` lists the top-level entries and totals without creating anything; `--json` prints one machine-readable summary.
   - `--from default --to work2` copies `profiles/camoufox/default` to `profiles/camoufox/work2`.
3. **Set Account profile to the copy** (`work2` above) and restart Claude Code. The copy starts signed in wherever the source was signed in.
4. **Copied:** cookies, logins, local storage, `Local State`, `Preferences`, the device identity file `.camoufox-identity.json`, and every `*.sqlite-wal` / `*.sqlite-shm` companion of a database (`cookies.sqlite-wal` and `-shm` are part of the database, not a cache). **Not copied:** the bridge profile lock, Firefox's `parent.lock`, the session store files, `cache2`, `startupCache`, `thumbnails`, Chromium's singleton files and caches (absent in a Firefox profile anyway), `*.tmp` entries and log directories. The browser rebuilds the caches on first use. The report names the engine-specific exclusions it removed. **A copy carries no session cookies**: Firefox keeps them in memory, not on disk.
5. **The optional `.proxy` file is not copied.** `profiles/camoufox/work2.proxy` does not appear: the file is a plaintext credential, so the tool never duplicates it silently. Copy it yourself (and `chmod 600` it on POSIX) only if the copy should use the same proxy.
6. **Same identity, or a fresh one.** Because the seed is copied, the copy keeps the source fingerprint, which is what makes it useful. To give the copy a fresh fingerprint, close the browser and delete `<copy>/.cloakbrowser-seed` before the first start; the engine then writes a new seed. The copy tool never deletes or edits the seed for you.
7. **No CloakBrowser seat is involved.** Camoufox is not Cloak-licensed; two Camoufox sessions can run on different profiles, each with its own process. The free CloakBrowser tier still allows one browser at a time, and a copy never adds a CloakBrowser seat.
8. **Refusals are complete:** an invalid name, a missing source, an existing destination (never overwritten, never merged), a live or unreadable bridge lock, and a live `parent.lock`. A failed copy removes only the destination directory it created, never the source and never a directory another process made.

## Sign-in

Sign in to Google or any site manually, in the headed window, with the persistent profile. Automate only the logged-in session. **Never automate the Google credential form** — or any site's password, recovery, 2FA, passkey or CAPTCHA step.

Per account:

1. Set **Account profile** to the account name and restart Claude Code.
2. Ask the agent to open the site's sign-in page in the headed window (`headless` stays off).
3. The agent stops at the credential form and says it is waiting.
4. Type the email, password and any 2FA or CAPTCHA in that window yourself and finish the login.
5. The agent confirms the signed-in state by reading the page (name or avatar), never by reading secrets.
6. The session is stored in that account's profile directory and reused on the next start.

Never automated, for any account: the credential form, password entry, account recovery, 2FA or passkey prompts, CAPTCHA or bot challenges; account creation; copying cookies, storage state or a profile between accounts to skip a login. One account per profile, always.

Settings that the Camoufox engine cannot honour are **not declared**: `humanize`, `human_preset`, `release_channel`, `geoip_proxy_match`, `licence_key`, `engine_version`, `browser_engine`, `camoufox_profile`, `camoufox_data_dir`, `kameleo_profile_id` and `kameleo_endpoint`. `browser_capabilities.ignoredSettings` still reports the first six, because the shared manifest names them for the universal broker. CloakBrowser's humanised input, release channel, GeoIP proxy matching and licence do not exist in this engine.

## Profile and sessions

With the profile settings empty, the plugin uses `<plugin data>/profiles/camoufox/default` inside its own `${CLAUDE_PLUGIN_DATA}` (for example `.../data/camoufox-cloakbrowser-mcp/profiles/camoufox/default`). That directory is separate from the universal plugin's profile; cookies and logins are not shared. The browser engine locks a profile while a session uses it, so do not point two running sessions at the same directory. One directory per account; see [Accounts](#accounts) for the name setting.

### Default profile (applies at the next start)

The default-profile pointer is one line in `<plugin data>/profiles/camoufox/.default` naming the profile a start uses when neither Profile directory nor Account profile is set. Set it with the `browser_profiles` meta-tool (`action: "set-default"`, `name`) or with `scripts/profile-default.mjs` from a terminal (`--show`, `--set <name>`, `--dry-run`, `--json`, `--data-dir`; an installed copy lives at `<plugin root>/scripts/profile-default.mjs`, and the data root for this plugin is `%USERPROFILE%\.claude\plugins\data\camoufox-cloakbrowser-mcp`). This plugin ships only the `camoufox` engine, so the script needs `--engine camoufox`: its default engine is `cloak`, which this plugin does not contain and therefore rejects. Both paths validate the name with the account rule and write atomically. The change applies at the **next server start**; this session keeps its profile and no browser is started, stopped or reconfigured. A broken pointer is reported in `browser_capabilities.profileDefaultError`, logged once, and ignored for that start (the workspace profile or the engine default applies) — never fatal. A pointer-named profile is created on its first launch like an account, and `profiles/camoufox/<name>.proxy` is used beside it. Delete `<plugin data>/profiles/camoufox/.default` to remove it; the universal plugin's README documents the same mechanism in full.

### Profile isolation

**Profile isolation** (`profile_isolation`) has five values. `shared` (the default) is the previous behaviour byte for byte: every Claude Code window uses the same profile for the account, and a second window is stopped by the preflight below. `workspace` derives one profile per project folder, `<plugin data>/profiles/camoufox/ws-<sha256(cwd)[:7]>` (for example `ws-0b0e194`), Playwright-style. Different project folders never collide. A workspace profile starts with a **fresh login state** and its **own device identity** drawn on its first launch: cookies, logins and the identity file from `profiles/camoufox/default` are not carried over. An explicit Account profile or Profile directory keeps its exact previous meaning and wins over `shared`/`workspace`/`copy`/`copy-keep` isolation.

`copy` runs the session on a temporary whole-tree copy of the base profile and never writes to the base. The base is resolved exactly like `shared` (`profile_dir` → `account` → pointer → `profiles/camoufox/default`); `copy` does not combine with `workspace`. The broker runs the bridge-lock and Firefox `parent.lock` preflights first and **refuses loudly** if the base is live (owner and fix named, no copy made, no fallback), takes the base's lock in the bridge's own format for the session, then copies to `<plugin data>/profiles/camoufox/.sessions/<base>-<YYYYMMDD-HHMMSS>-<pid>` with the same exclusions as `scripts/profile-copy.mjs` (`cache2`, `startupCache`, `thumbnails`, `parent.lock`, locks, singletons, `*.tmp` and logs are not copied; every `*.sqlite-wal`/`-shm` is kept). Camoufox starts on the copy; the base keeps its bytes and is locked until the session ends, so a shared/workspace window cannot use it meanwhile. A clean shutdown deletes the copy and releases the lock (one log line says the copy was discarded); a hard kill keeps it, and `browser_profiles` lists it under `sessionCopies` (`current`, `active`, `leftover`) with its path — `scripts/profile-copy.mjs --prune` removes leftovers explicitly and never automatically. The device identity file travels inside the copy, so the session presents the same device as its base (delete `.camoufox-identity.json` inside the copy to give that session a different one). `camoufox-native` owns its profiles, so `copy` is refused loudly for it.

`copy-keep` is the same session as `copy` plus one rule: **the last clean close wins**. After the backend has exited, the broker waits (bounded to 5 s, never forced) for the session copy's own locks to be released, retries a transiently refused directory rename for up to 3 s, renames the base to `<base>.previous-<YYYYMMDD-HHMMSS>` (a same-second collision gets `-2`, …), renames the session copy into the base path, and only then removes the session-owner marker and releases the base lock. The retained previous tree is **user data**: `browser_profiles` lists it under `previousTrees` (bounded, newest first), the plugin never deletes it, and `--prune` still removes only leftover `.sessions` copies, so the trees accumulate until you remove them. The broker that swaps is exiting, so it writes `<plugin data>/profiles/camoufox/.last-swap.json` and the next session reports it as `lastSwap` (`state`, base, session copy, previous tree, restore flag, error); `browser_capabilities` and `browser_engine_status` report it too when it exists. A **hard kill performs no swap**: the base keeps its exact bytes and the session tree is retained and listed. If the second rename fails, the base is restored from the previous tree, the session copy is kept, and the failure names both paths. `copy-keep` is refused loudly when the base resolves outside the plugin data directory (a whole-tree swap on an arbitrary real profile) — `copy` stays allowed there — and it is refused for `camoufox-native` exactly like `copy`.

`isolated` uses **no browser profile at all**. The broker removes any user-data-dir and sets `PLAYWRIGHT_MCP_ISOLATED=true`; `camoufox-playwright-mcp` reads that variable (`mcp/config.py`) and launches a non-persistent browser, and the launcher skips its default-profile creation, so no profile directory is created, locked or written. Cookies, logins and other browser state are not saved and nothing persists after the session — the wording is deliberately not "in memory". Account profile, Profile directory and the default-profile pointer are ignored for that start and reported in `profileIgnored` with the value supplied; `browser_capabilities`, `browser_engine_status` and `browser_profiles` report `profileIsolation: "isolated"`, `profileDir: null`, `profileSource: "isolated"`, `profileLock: null` and a note that the pointer and set-default do not affect the session, and `initialize.instructions` gains one sentence saying nothing persists. The profile is not locked, so several isolated sessions can run at once. An isolated session has nowhere to store a device identity, so it draws a fresh one on every launch whatever Device identity says; the meta-tools report `identitySource: "isolated"` and the instructions say so.

### Device identity

Camoufox draws a new device fingerprint on every launch unless the caller pins one, and its own code names the pattern a returning site sees — identical cookies, a changed font or voice list — as a spoof tell (daijro/camoufox#442, #765, #378). **Device identity** (`identity_mode`, default `profile`) fixes that for persistent profiles:

- **`profile`** (default): the first launch of a profile draws a fingerprint with Camoufox's generator for **this computer's operating system**, writes it to `<profile>/.camoufox-identity.json` (with `createdAt` and the browser build it was generated for), and passes it to the wrapper on every later launch through a per-profile config file under `<plugin data>/config/camoufox/`. The same profile therefore keeps the same user agent, platform, screen geometry, GPU, fonts, voices, media devices and audio seed across launches, while cookies and logins persist as before. Camoufox re-writes the user-agent version to the running build, so a browser update does not freeze an old version in the identity. The identity is machine-bound through the hardware-concurrency value Camoufox takes from the host: a profile moved to another machine keeps its user agent, screen and GPU but may redraw fonts and voices.
- **`random`**: no identity file is read or written; every launch draws a new device, exactly as before 2.14.0. Use it when a fresh device per launch is what you want.
- **Rotation** is file deletion: remove `<profile>/.camoufox-identity.json` and the next start draws and stores a new identity. There is no tool and no automatic rotation. Copies of a profile carry the file, so a base and its copies present the same device; delete the file inside a copy to give that copy its own.
- **Corruption**: an unreadable or malformed identity file is removed, regenerated and reported with one stderr line and in the next `browser_capabilities.identityNote`; the server never fails to start over it. If the fingerprint cannot be generated at all (for example the generator's pinned model cannot be fetched), that start keeps a random identity and says so on stderr.
- **Your own wrapper config is never edited.** The wrapper reads its non-obvious options from a file named by `CAMOUFOX_MCP_CONFIG` (or `PLAYWRIGHT_MCP_CONFIG`); there is no environment variable for a fingerprint. If you already point either variable at a JSON file, the plugin writes a copy under its data directory with `browser.camoufoxOptions.fingerprint` (and `os`) merged in, your own keys kept, and points the engine at the copy; a key you already set is replaced **in the copy only**, with one stderr line saying so. An INI or unreadable file is left untouched, so `identity_mode` is not applied on that start and the meta-tools report `identitySource: "random"` with the reason.
- **Reporting:** `browser_capabilities` and `browser_engine_status` report `identityMode`, `identityApplies`, `identitySource` (`profile-file`, `random`, `isolated`), `identityFile`, `identityCreatedAt` and, when there is something to say, `identityNote`. `initialize.instructions` gains one sentence for the active mode. No new tool.
- **Workspace profiles** get their own identity file in their own directory on first launch; `copy` and `copy-keep` run on a tree that carries the base's file, so they present the same device.

The `camoufox-native` engine cannot be fixed from this side: `mcp-camoufox` 0.4.5 has no fingerprint input, so each of its browser starts draws a new device identity and `identity_mode` is inert there (reported as `identitySource: "native-unavailable"`).

### Lock preflight and fallback

Before starting the backend, the broker reads the bridge's profile lock (`<profile>/.cloakbrowser-mcp-profile.lock`) and:

- With a **live owner**, it does not start a doomed backend. The meta-tools answer, and the same plain-language sentence (directory, owner PID and start time, and the fix) appears in `initialize.instructions`, `browser_capabilities.engineError`/`profileLock` and `browser_engine_status.lastError`/`profileLock`. `profileLock.state` is `free`, `live`, `stale` (owner gone; the bridge reclaims it) or `invalid` (unreadable lock file; the fix names it). The plugin never deletes a lock or a profile.
- Camoufox also declares Firefox's own `<profile>/parent.lock` in its manifest, reported as the additive `engineProfileLock` key (`{ state, profileDir, path, file, liveness, owner, error, fix }`). `liveness` is `exclusive-open`: the broker reads the file, so a live browser's exclusive handle makes it unreadable and the start is refused with the same loud wording; a zero-byte lock left by an exited browser reads as `stale` and does not block.
- With `profile_isolation=workspace` and the derived workspace profile busy, it uses the first free numbered sibling (`ws-<hash>-2` … `ws-<hash>-5`) and reports `profileFallback: { from, to, reason }` in both meta-tools and in `initialize.instructions`. The fallback is a different identity; it is always announced. When all five are in use, no backend starts and the error says so.
- With `shared`, there is **no fallback**: a busy profile is never silently swapped for another identity.

The preflight narrows the race but the engine remains the authority; its last stderr line is now reported for every engine, including this one, and credential-bearing proxy URLs are redacted.
