# cloakbrowser

Claude Code plugin that gives the agent the Playwright MCP tool contract (72 `browser_*` tools: snapshots with element refs, clicks, forms, tabs, console, network, tracing, video) running on CloakBrowser, a stealth-patched Chromium, on Camoufox, a stealth Firefox, on Camoufox's own native MCP server, or on a Kameleo Chroma profile over CDP.

A local broker selects the engine and tool profile from the plugin settings. With the default `cloak` engine and the default `full` profile the plugin exposes **77 tools**: the 72 backend browser tools, two local diagnostics (`cloakbrowser_binary_info`, `cloakbrowser_bridge_info`) and three broker meta-tools (`browser_capabilities`, `browser_engine_status`, `browser_profiles`). The `portable` profile exposes **27 tools**: one shared 24-tool browser core plus the three meta-tools; backend-specific and extra tools, including the two local diagnostics, are hidden. The `camoufox` engine defaults to `portable` and exposes **27** tools by default (**70** at `full`). The `camoufox-native` engine defaults to `portable` and exposes **17** tools (14 canonical aliases plus the three meta-tools); `full` exposes **28** (16 canonical aliases + 9 prefixed native tools + 3 meta). The `kameleo` engine defaults to `portable` and exposes **27** tools; `full` exposes **75** (72 browser tools + 3 meta), because this path bypasses the Cloak bridge and its two local diagnostics.

For the Chromium engines the broker starts `launch.mjs`, which launches `cloakbrowser-mcp`; that package starts the official `@playwright/mcp` server and points it at the selected browser. For Camoufox it starts `launch-camoufox.mjs`, which provisions a pinned `uv`, a managed Python and a venv with `camoufox-playwright-mcp`, then starts it. For Camoufox native it starts `launch-camoufox-native.mjs`, which fetches `mcp-camoufox` from PyPI into a plugin-managed venv and starts it. For Kameleo it starts `launch-kameleo.mjs`, which reuses the plugin's pinned runtime and starts the official `@playwright/mcp` CLI against Kameleo's local CDP WebSocket. Tool names and schemas are Microsoft's; parity is structural, not reimplemented.

## Install

From this repository:

```
/plugin marketplace add FiredMosquito831/cloakbrowser-mcp
/plugin install cloakbrowser@cloakbrowser-mcp
```

From a local checkout:

```
/plugin marketplace add D:\Projects2\StealthBrowserAutomation\fork
/plugin install cloakbrowser@cloakbrowser-mcp
```

Claude Code prompts for the settings below during install. You can also pass them non-interactively:

```bash
claude plugin install cloakbrowser@cloakbrowser-mcp \
  --config headless=false \
  --config profile_dir=/home/you/.cloakbrowser-profiles/linkedin \
  --config proxy_server=http://user:pass@host:port
```

Change them later with `/plugin` → Configure, the per-option rows in `/config`, or:

```bash
claude plugin configure cloakbrowser@cloakbrowser-mcp

# non-interactive: a JSON object of single-line strings on stdin
printf '%s' '{"profile_dir":"/home/you/.cloakbrowser-profiles/linkedin"}' | \
  claude plugin configure cloakbrowser@cloakbrowser-mcp --values-stdin
```

Non-sensitive values are stored under `pluginConfigs` in your user settings; the licence key goes to the operating system credential store. Restart Claude Code after a change so the MCP server restarts with the new environment.

## Per-engine plugin

This plugin is the universal broker: one MCP server whose **Browser engine** setting selects `cloak` (default), `playwright`, `camoufox`, `camoufox-native` or `kameleo`. It stays the default, and every prompt, permission rule or saved transcript written against `mcp__plugin_cloakbrowser_cloakbrowser__*` keeps working.

The marketplace also ships **`camoufox`**, a separate plugin fixed to the Camoufox contract engine (`STEALTH_ENGINE=camoufox`, server key `camoufox`, tool names `mcp__plugin_camoufox_camoufox__*`). Choose it for a single-engine install that declares only the settings the Camoufox engine honours; its plugin configuration is separate and is not carried over from this plugin. Do **not** install both plugins for the same engine: each starts its own broker, runtime and profile. A Kameleo per-engine plugin is **not** shipped; Kameleo remains an engine of this universal broker, with its live behaviour unverified.

Both plugins share a generated core. Edit `shared/core/` and run `node scripts/sync-plugin-core.mjs --write` from the repository root; never edit a plugin copy directly.

## Requirements

- Node 22.13+ or 24+ (the plugin and the npm runtime).
- **Nothing else is a manual prerequisite for `cloak`, `playwright`, `camoufox` or `camoufox-native`.** Every local dependency is provisioned into Claude Code's plugin data directory at the first MCP server start: the npm runtime, a pinned and checksum-verified `uv`, a managed CPython, and the engine's Python venv. No Python, uv, pip, pipx or `uv tool` install is needed, nothing is installed system-wide, and no launcher starts a shell.
- **A `uv` you provide must be 0.13.5 or newer.** The plugin pins `uv` 0.13.5 because that release installs the managed CPython 3.13.17; older ones fail with `No download found for request: cpython-3.13.17-windows-x86_64-none`, and the Camoufox launchers then exit. A `uv` on `PATH` older than 0.13.5, or one that does not answer `--version`, is ignored with one log line and the plugin provisions its own pinned copy. An explicit `UV`/`UV_BIN` older than 0.13.5 is refused with the version it reported: the plugin never silently replaces your explicit choice.
- **The first start may take seconds to several minutes.** The largest item is the Camoufox browser build (about 1.3 GB); everything else is tens of megabytes. If Claude Code's MCP startup timeout expires during a first download, restart Claude Code (`/reload-plugins`): the next start reuses what was already provisioned and does not download it again.
- The first launch installs the MCP and its pinned engine wrapper into Claude Code's plugin data directory, then downloads the CloakBrowser Chromium binary (~200 MB) into `~/.cloakbrowser` on the first browser call. Nothing binary is committed to this repository.
- With the profile settings empty, the plugin uses its own persistent profile at `<plugin data>/profiles/default`. It is a real on-disk profile, not a temporary one, and it survives plugin updates. **Profile isolation** (`shared`, the default) can instead derive one profile per project folder, or use no profile at all — see [Session safety and profile isolation](#session-safety-and-profile-isolation).
- The MCP runs on **Patchright 1.64.1** instead of stock Playwright. Stock Playwright's CDP control channel sets `isAutomatedWithCDP` on fingerprint tests; Patchright keeps the same Playwright API and avoids it. The bridge's console fallback is disabled for the same reason, and console capture still works.
- **Camoufox first launch is large.** The launcher creates a venv at `<plugin data>/venvs/camoufox` and installs `camoufox-playwright-mcp==0.1.5` plus its Camoufox dependency. It then ensures the pinned Camoufox build `v156.0.1-beta.39`; when absent, that is a **~1.3 GB download and ~2.4 GB on disk** in Camoufox's machine-wide cache. Plan for the time and space; the browser itself starts on the first browser tool call, not at `initialize`.
- **The Camoufox venv pins the Python MCP stack.** Alongside the wrapper it installs `fastmcp==3.4.7` and `mcp==1.29.0`, the versions the wrapper's own `uv.lock` resolves. The wrapper's `pyproject.toml` declares only `fastmcp>=3.4.2`, with no upper bound, so an unpinned install resolves fastmcp 4.x; that major answers in the 2026-07-28 protocol era, where every request gets a new session id, and the wrapper keys its browser backend by that id. The result is a new browser on every tool call, and the second launch fails on the profile the first browser still holds (`exitCode=0`). The pins are part of the venv marker, so an existing venv rebuilds itself on the next start; `CAMOUFOX_MCP_PACKAGE` still overrides the wrapper pin, and the stack pins stay. The pin is revisited when upstream bounds `fastmcp` itself or keys its backend by a stable id.
- **Camoufox cache side effect.** Camoufox stores builds in a machine-wide user cache (`%LOCALAPPDATA%\camoufox` on Windows), and its installer makes the build it installs the active one. Installing the pin can therefore move another Camoufox consumer on this machine to `v156.0.1-beta.39`. This engine's own launches stay pinned through `CAMOUFOX_EXECUTABLE_PATH` regardless of which build is active.
- **Windows and the Camoufox engine.** The pinned wrapper's stdio server installs a signal watchdog through anyio, which Windows does not implement; without a fix the server exits before answering `initialize`. `camoufox_entry.py` replaces only that receiver with an empty one (the broker owns shutdown on every platform) and then runs the unmodified wrapper. On other platforms the shim is not installed.
- **The `camoufox-native` engine fetches `mcp-camoufox` from PyPI itself.** At the first start the launcher provisions `mcp-camoufox==0.4.5` into `<plugin data>/venvs/camoufox-native` and uses its console script. The plugin never bundles or redistributes the package; its licence is **FSL-1.1-MIT** (source-available, not OSI); provisioning it is a download from the public index, the same decision as installing it yourself. If provisioning fails, an explicit `CAMOUFOX_NATIVE_COMMAND` wins and a usable `mcp-camoufox` on `PATH` is the fallback; when neither exists the launcher exits with one actionable line, and the broker answers `initialize` with only the three meta-tools so `browser_engine_status` can report the failure. This is the **PyPI `mcp-camoufox`** (27 tools); the npm package of the same name is a different 133-tool project.
- **Camoufox native first call.** The app owns the browser download: when the pinned build `156.0.1-beta.39` is absent it downloads on the first browser tool call, which is slow. `initialize` and `tools/list` answer from the static tool registry first.
- **Camoufox native profiles.** `CAMOUFOX_DATA_DIR` defaults to `<plugin data>/profiles/camoufox-native`. The app always creates `<data dir>/profiles/<name>`, so the on-disk profile is `<plugin data>/profiles/camoufox-native/profiles/<name>` — the doubled `profiles/` segment is the app's layout, not a typo. Profile names are 1–64 characters, start alphanumeric, and use only letters, digits, `.`, `_` and `-`; a slash is impossible. One name per account; with the daemon off, a second session naming the same profile is refused by the app.
- **Camoufox native daemon is off.** v2.3.0 pins `CAMOUFOX_DAEMON=false`. The broker can only own its own child tree; a detached, lease-driven daemon would outlive it by design, so daemon mode is not exposed.
- **Camoufox native fingerprint OS defaults to the host.** When `CAMOUFOX_FINGERPRINT_OS` is unset, the launcher sets it to the host OS in Camoufox's vocabulary (`win32` → `windows`, `darwin` → `macos`, `linux` → `linux`), so the claimed persona matches the machine that renders the GPU/user-agent stack. An explicit `CAMOUFOX_FINGERPRINT_OS` wins (case and surrounding whitespace are normalised). An invalid value falls back to the host default and logs one line instead of failing. This is not a plugin setting: set it in the environment before starting Claude Code. The 2026-10-24 detector runs showed why it matters: random macOS personas on this Windows host tripped `hasInconsistentTimingResolution`, while Windows-pinned personas passed cold and warm.

### What is installed at first launch

Measured on the build machine on 2026-10-24 with a fresh plugin data directory and no `uv` on `PATH`; times are the first server start (broker plus provisioning), and disk is the plugin data directory after it (`du`, hard links counted once).

| Engine | Provisioned under `<plugin data>` | Source host | Disk | First start |
|---|---|---|---:|---:|
| `cloak`, `playwright` | `runtime/`: `cloakbrowser-mcp@1.15.1` with Playwright aliased to `patchright@1.64.1` | registry.npmjs.org | 64 MB | ~7 s |
| `kameleo` | the same `runtime/` (Kameleo itself is **not** installed; see below) | registry.npmjs.org | 64 MB | ~7 s |
| `camoufox` | `tools/uv/0.13.5`, `tools/python/3.13.17`, `venvs/camoufox` (`camoufox-playwright-mcp==0.1.5`, `fastmcp==3.4.7`, `mcp==1.29.0`), `cache/uv` | github.com (uv release; Python builds), pypi.org / files.pythonhosted.org | 391 MB | ~28 s |
| `camoufox-native` | `tools/uv/0.13.5`, `tools/python/3.13.17`, `venvs/camoufox-native` (`mcp-camoufox==0.4.5`), `cache/uv` | github.com (uv release; Python builds), pypi.org / files.pythonhosted.org | 456 MB | ~28 s |

The Camoufox browser build (about 1.3 GB download, ~2.4 GB on disk) is separate and lives in Camoufox's machine-wide cache; it is not counted above and is only downloaded when absent. The CloakBrowser Chromium binary (~200 MB) is downloaded into `~/.cloakbrowser` on the first browser call, not at server start. A second start reuses everything: measured 0.5–3.3 s with no download.

**Overrides (environment variables, not plugin settings):**

| Variable | Effect |
|---|---|
| `UV`, `UV_BIN` | Use this `uv` instead of `PATH` or the pinned copy. It must be 0.13.5 or newer: a broken, older or unanswering value fails instead of falling back |
| `UV_PYTHON`, `PYTHON` | Use this interpreter (a path or a uv Python request) instead of the managed CPython. `UV_PYTHON` wins |
| `CAMOUFOX_NATIVE_COMMAND` | Use this `mcp-camoufox` executable instead of provisioning or `PATH` |
| `CLOAK_PLAYWRIGHT_MCP_PACKAGE`, `CAMOUFOX_MCP_PACKAGE`, `CAMOUFOX_NATIVE_PACKAGE` | Override the pinned package (the marker detects the change and rebuilds the runtime or venv) |
| `CAMOUFOX_BROWSER_BUILD`, `CAMOUFOX_NATIVE_BROWSER_BUILD` | Override the pinned Camoufox browser build |

Only the official uv release (SHA-256 verified against the checksum embedded in `lib/provision.mjs`), the Python builds uv resolves, the package index (PyPI by default), npm's registry and the Camoufox release index are contacted. Nothing is written to the user `PATH`, the Windows registry, `~/.local/bin` or a system Python site; `uv python install` runs with `--no-bin --no-registry`, and `UV_PYTHON_INSTALL_DIR`, `UV_CACHE_DIR` and the venvs all live under the plugin data directory.

- **The `kameleo` engine needs the Kameleo desktop app.** Kameleo is a commercial desktop application and is **not** a package the plugin can provision: the plugin never downloads, installs, runs or starts it, and there is no package-manager path (the build machine has no `winget`). Install it yourself:
  1. Download the Windows installer from <https://kameleo.io/downloads> (`Kameleo.Installer.exe`, about 150 MB; the vendor lists Windows 10 or newer).
  2. Run the installer and start Kameleo.
  3. Create or select a **Chromium (Chroma)** profile; a Junglefox (Firefox) profile cannot be attached over CDP.
  4. Copy the profile ID into **Kameleo profile ID** (`kameleo_profile_id`), select the `kameleo` engine and restart Claude Code.

  The vendor's download page states on 2026-10-24 that no account is needed and that a free tier exists; that is **vendor-reported and was not tested here**. `browser_capabilities.systemDependencies` reports the app as `unknown` until there is evidence, then `missing` with this same install hint in `browser_engine_status.lastError`. The free tier allows 2 concurrent profiles; licence or profile-start failures surface as the tool error, not as a plugin bug.
- **Kameleo endpoint.** With the endpoint setting empty, the launcher uses `ws://127.0.0.1:5050/playwright/<profile ID>`. `127.0.0.1` and `localhost` are the same local listener; the plugin uses the literal IPv4 loopback for determinism. The optional **Kameleo CDP endpoint** setting is a full override and is accepted only when it parses as a `ws://` or `wss://` URL whose host is `127.0.0.1`, `::1` or `localhost`, with no username or password and a port in 1–65535; a path is allowed, so a raw `devtools/browser/...` URL can be pasted. Anything else is rejected at startup with one line naming the setting and the failed rule. Non-loopback endpoints are rejected because a CDP endpoint is full browser control and this plugin's scope is local engines.
- **Lazy connection.** `initialize` and `tools/list` answer without Kameleo running: the official Playwright MCP CLI lists its tools from static schemas and creates a browser only on the first browser tool call. That call makes a local TCP attempt; when nothing listens on 5050 it fails after the CLI's 30-second CDP timeout and returns an `isError: true` tool result. The broker appends one sentence to that result until a tool call succeeds:
  `Kameleo is not answering at ws://127.0.0.1:5050/playwright/<profile ID>. Start the Kameleo app, sign in, and confirm the profile ID exists. Kameleo starts the profile itself when the endpoint is opened.`
  The exact offline error recorded on 2026-10-24 was:
  ```
  Error: async initializeServer: WebSocket error: connect ECONNREFUSED 127.0.0.1:5050
  Call log:
    - <ws connecting> ws://127.0.0.1:5050/playwright/<profile ID>
    - <ws error> ws://127.0.0.1:5050/playwright/<profile ID> error connect ECONNREFUSED 127.0.0.1:5050
    - <ws connect error> ws://127.0.0.1:5050/playwright/<profile ID> connect ECONNREFUSED 127.0.0.1:5050
    - <ws disconnected> ws://127.0.0.1:5050/playwright/<profile ID> code=1006 reason=
  ```
  A missing profile ID is different: it is a configuration error before any process starts. `initialize` answers with that reason, `tools/list` returns only the three meta-tools, `browser_engine_status.backendState` is `failed`, and `browser_capabilities.engineError` carries the exact sentence naming `kameleo_profile_id`.
- **The Kameleo runtime is the cloak runtime.** `launch-kameleo.mjs` starts the pinned `@playwright/mcp` CLI inside `<plugin data>/runtime`, the tree `launch.mjs` installs (`cloakbrowser-mcp@1.15.1`, Playwright aliased to Patchright 1.64.1). It does not go through `cloakbrowser-mcp` and does not start `patchright mcp`. A healthy runtime is reused; if it is absent or its pin marker does not match, the launcher provisions it with the same package, overrides and marker as `launch.mjs`, then starts the CLI with `--cdp-endpoint`. This first provisioning needs npm and takes the same 10–20 seconds the cloak engine's first launch takes.
- **Kameleo settings that do not apply.** The profile, its cookies, its logins and its proxy are Kameleo's. `profile_dir`, `proxy_server`, `proxy_bypass`, `humanize`, `human_preset`, `release_channel`, `geoip_proxy_match`, `licence_key`, `engine_version`, `headless`, `camoufox_profile` and `camoufox_data_dir` are ignored by this engine and are reported in `browser_capabilities.ignoredSettings`. `output_dir`, `tool_profile`, `disabled_tools` and the seven tool groups still apply.
- **Kameleo is UNVERIFIED.** Kameleo is not installed on the machine this release was built on, and nothing listens on TCP 5050. The adapter, the lazy handshake, the error path and the tool surface were verified offline; **no CDP attach and no detector run were performed, and no stealth claim is made for this engine.** The central unknown is whether Patchright in attach mode suppresses CDP tells; `connectOverCDP` is also documented by Playwright as lower fidelity for traces, video and some routing. Install Kameleo, activate a licence, create a Chroma profile and provide its ID, then record `isBot`, the CDP flags, timing, WebGL and console before treating the engine as validated. `browser_close` is marked `partial` because it closes the attached context and may close the Kameleo profile window; tracing is `partial`; video, recording and annotation are `unknown`. These are exposed at `full` and a call fails with the backend's own message.
- **Kameleo has no local diagnostics.** This path bypasses the Cloak bridge, so `cloakbrowser_binary_info` and `cloakbrowser_bridge_info` do not exist for it. The surface is 72 browser tools + 3 broker meta-tools = **75** at `full`, and 24 + 3 = **27** at `portable`.

The engine wrapper is pinned to `cloakbrowser@0.6.3` because the bridge (1.15.1) rejects `0.6.4` when humanize is enabled. The pin is in `launch.mjs` and is removed once the bridge accepts the newer wrapper. The Camoufox pins are in `launch-camoufox.mjs` and `.mcp.json` (`CAMOUFOX_MCP_PACKAGE`, `CAMOUFOX_BROWSER_BUILD`); the venv also pins `fastmcp==3.4.7` and `mcp==1.29.0` from the wrapper's `uv.lock`, because the wrapper leaves `fastmcp` unbounded and fastmcp 4.x breaks the tool-call lifecycle. The Kameleo launcher reuses the Cloak runtime and pins the same package, wrapper and driver identities; a unit test keeps the two launchers' constants equal.

## Settings

Values live in Claude Code's plugin configuration, not in this repository. Non-sensitive values are stored in `pluginConfigs` in `settings.json`; the licence key goes to the operating system credential store.

| Setting | Default | What it does |
|---|---|---|
| Headless | `false` | Headed is measurably less detectable. Turn on only for a display-less server |
| Browser engine | `cloak` | `cloak` runs the patched CloakBrowser Chromium. `playwright` falls back to stock Chromium and loses the stealth patches. `camoufox` runs the Camoufox stealth Firefox through `camoufox-playwright-mcp`; its Python runtime is provisioned automatically. `kameleo` attaches to a running Kameleo Chroma profile over CDP and needs the separately installed app, a licence and a profile ID. The broker reads this when the MCP server starts; restart Claude Code after changing it |
| Tool profile | `default` | `default` follows the selected engine's manifest: `full` for `cloak` and `playwright`, `portable` for `camoufox`, `camoufox-native` and `kameleo`. `portable` exposes the shared 24-tool browser core; `full` exposes everything the engine supports. The seven tool groups and `disabled_tools` still apply. Restart Claude Code after changing it |
| Camoufox native profile | `default` | Profile name for the `camoufox-native` engine. Letters, digits, `.`, `_` and `-`, starting with a letter or digit, up to 64 characters. One name per account; cookies and logins live under it |
| Camoufox native data directory | empty → `<plugin data>/profiles/camoufox-native` | Where the native engine keeps `profiles/<name>` and `logs/`. Use one directory per set of accounts |
| Kameleo profile ID | empty | Required when the browser engine is `kameleo`. The ID of a Chromium (Chroma) profile in Kameleo. The plugin never starts the app; it connects to Kameleo's local API, which starts the profile. Junglefox profiles cannot be attached over CDP |
| Kameleo CDP endpoint | empty → `ws://127.0.0.1:5050/playwright/<profile ID>` | Optional full WebSocket endpoint. Only `ws://` or `wss://` on `127.0.0.1`, `::1` or `localhost`, without userinfo, is accepted |
| Tool groups | all on | Seven checkboxes: vision, pdf, devtools, storage, network, testing, config. Turn one off to remove that group |
| Disabled tools | empty | Comma-separated tool names hidden from `tools/list` and rejected on call |
| Humanised input | `true` | Human-like mouse paths, keystroke timing and scrolling |
| Humanised preset | `default` | `careful` is slower and more deliberate |
| Release channel | `stable` | `preview` requires a Pro licence |
| GeoIP proxy match | `false` | Aligns timezone and locale to the proxy exit; enable with a proxy |
| Profile isolation | `shared` | `shared` keeps one profile per account for every Claude Code window, exactly as before. `workspace` derives one profile per project folder (`profiles/<engine>/ws-<hash>`) with a fresh login state, and moves to a numbered sibling if that profile is already in use. `isolated` uses no profile at all: nothing is created or locked, cookies, logins and storage are not saved, and nothing persists after the session; Profile directory, Account profile and the default-profile pointer are ignored and reported for that start. `copy` runs the session on a temporary copy of the profile that Profile directory, Account profile, the default-profile pointer or the engine default resolves; the base is locked for the session and never written, and the copy is discarded on a clean shutdown (a crashed session leaves it under `profiles/<engine>/.sessions`, listed by `browser_profiles` and removed only by `scripts/profile-copy.mjs --prune`). `copy-keep` does the same and keeps the changes: a clean close replaces the base with the session copy and retains the old base beside it as `<name>.previous-<timestamp>`, which is never deleted automatically and accumulates until you remove it; a crash performs no swap. `copy-keep` is refused when the base is outside the plugin data directory. `copy` and `copy-keep` do not combine with `workspace`. In `shared`, `workspace`, `copy` and `copy-keep`, Account profile and Profile directory win over the mode. The free CloakBrowser tier still allows one browser at a time. See [Session safety and profile isolation](#session-safety-and-profile-isolation) |
| When the profile is in use | `fallback` | What this session does when the profile it resolved is already held by another process. `block` is the 2.15 behaviour: no backend starts and only the broker meta-tools answer until Claude Code restarts the server. `fallback` — the default — never starts a second CloakBrowser: the session **holds** the profile, keeps its tool list from a cache and retries on every tool call, so close the other session and call a tool again (no restart). `isolated` starts with no profile at all. On the engines without a seat limit (`playwright`, `camoufox`) `fallback` instead moves to the first free numbered sibling (`<name>-2` to `<name>-5`) with a separate identity. `block` is meta-only everywhere. See [When the profile is in use](#when-the-profile-is-in-use) |
| Device identity (Camoufox) | `profile` | Applies to the `camoufox` engine. `profile` gives each persistent Camoufox profile one generated device identity: the first launch draws a fingerprint for this computer's operating system, stores it in `<profile>/.camoufox-identity.json` and reuses it on every later launch, so a site that keeps cookies also sees the same device. Delete that file to draw a new identity on the next start; copies of the profile carry it, so delete it inside a copy to give the copy a different device. `random` restores the per-launch draw; an isolated start has no profile and always draws a new identity. The setting is inert for the other engines: `cloak` pins its own Chromium seed, `playwright` and `camoufox-native` have no fingerprint input, and Kameleo owns its profiles; `browser_capabilities` says so and reports `identitySource`, `identityFile` and `identityCreatedAt` |
| Server heartbeat timeout (Camoufox) | `0` | Applies to the `camoufox` engine: how long its backend waits for an answer to its own heartbeat ping, in milliseconds. `0` disables the wrapper's heartbeat (a ping every 3 s that closes the browser when an answer is more than 5 s late); a positive value re-enables it with that deadline. An explicit `PLAYWRIGHT_MCP_PING_TIMEOUT_MS` in the environment wins. The other engines send no server heartbeat and ignore it |
| Saved logins and autofill (Camoufox) | `false` | Applies to the `camoufox` engine. When on, Firefox's own password manager is enabled for the profile: saved logins in `logins.db` can be autofilled into matching login forms and Firefox offers to save new ones. A deliberate security trade-off — a page and the model can read filled credentials and a prompt-injected page can steer the model to a login form; the store travels with a copied profile. Plain-HTTP autofill stays off. The engine always runs on a plugin-owned overlay of the build (hardlinks and junctions; it restores the stock search engines — see [Camoufox search engines](#camoufox-search-engines)); turning this setting on adds the two password policies and the three signon prefs to that same overlay. See [Saved logins and autofill](#saved-logins-and-autofill) |
| Account profile | empty → the plugin's default profile | One profile per account: `profiles/<engine>/<name>`, and `default` reaches the existing `profiles/default`. Wins over Profile isolation; ignored when Profile directory is set. Restart after changing it. See [Accounts](#accounts) |
| Profile directory | empty → `<plugin data>/profiles/default` | Explicit profile path; wins over Account profile and Profile isolation. Persistent cookies, logins and fingerprint seed (for `camoufox`: the device identity file). One directory per account |
| Proxy server / bypass | empty | Sticky proxy and hosts that skip it |
| Licence key | empty | CloakBrowser Pro key; the free tier allows one concurrent session |
| Engine version pin | empty | Pin a specific Chromium build; empty follows the stable channel |
| Artifacts directory | empty | Where screenshots, traces and session files are written. Empty means `.playwright-mcp` inside the client's first usable `file://` root (the project folder Claude Code opened), or `<plugin data>/output/<engine>` when the client advertises no usable file root; `browser_capabilities.outputDir` reports the effective directory |
| Unrestricted file access | `false` | Removes Playwright's file-access allowlist for tool-chosen paths and unblocks `file://` navigation, so the model can read and write any file your operating-system user can. A deliberate security trade-off: a prompt-injected page could make the model read or overwrite private files. Leave it off unless you need a path outside the Artifacts directory and the workspace root. Applies to `cloak`, `playwright`, `camoufox` and `kameleo`; `camoufox-native` has no file-path tools and ignores it (`browser_capabilities.ignoredSettings`) |

The launcher drops empty optional values before starting the server, so leaving a directory or proxy blank behaves as "not configured" rather than as an empty path.

### Artifact paths and file access

Screenshots, traces and saved files go under the **Artifacts directory** (`output_dir`). When that setting is empty the broker chooses the directory **before the engine starts**: `.playwright-mcp` inside the client's first usable `file://` root — the project folder Claude Code opened — or, when the client advertises no usable file root (or does not answer the roots request within 2 s), `<plugin data>/output/<engine>`. The chosen directory is passed to the engine as `PLAYWRIGHT_MCP_OUTPUT_DIR`, the variable the Cloak bridge honours, so the allowlist and the artifacts agree by construction. The Playwright MCP server accepts an absolute path only inside one of two roots, the artifact directory and the client workspace, and refuses the rest with `File access denied: <path> is outside allowed roots`. Through the Cloak bridge the client's roots never reach the backend, so that workspace root falls back to the server cwd. `browser_capabilities` reports all three facts — `serverCwd`, `outputDir`, `clientRoots` — so a refused path can be explained instead of guessed at. The broker asks the client for its roots during the `initialize` handshake when the artifact directory depends on them, and lazily on the first `browser_capabilities` call when the setting already fixed the directory: one read-only `roots/list` request with a 2 s bound, cached for the session, reported as `clientRootsError` when the client did not advertise the capability, refused, answered with an error, or stayed silent. To write elsewhere, set the Artifacts directory. `camoufox-native` manages its own artifact files, so it reports `outputDir: null` and the setting does not apply to it.

**Unrestricted file access** (`allow_unrestricted_file_access`, default off) removes that allowlist for tool-chosen paths and also unblocks `file://` navigation. When it is on, the model may read and write **any file your operating-system user can**, not only the two roots — including files outside the project. That is a deliberate security trade-off, not a convenience: a prompt-injected page could ask the model to read credentials or overwrite a private file, and the plugin cannot distinguish that from your own request. Leave it off unless a workflow needs a path outside the roots; when you can, prefer setting the Artifacts directory instead. It applies to the `cloak`, `playwright`, `camoufox` and `kameleo` engines; `camoufox-native` exposes no file-path tools and lists the setting in `browser_capabilities.ignoredSettings`. When the setting is off or unset the launcher does not pass the variable to the engine, so the default configuration is unchanged.

### Saved logins and autofill

**Saved logins and autofill (Camoufox)** (`password_manager`, default **off**) enables Firefox's own password manager for the `camoufox` engine. When it is on, saved logins in the profile's `logins.db` can be autofilled into matching login forms and Firefox will offer to save new logins. This is a deliberate security trade-off, not a convenience. Autofilled credentials can be read by the page's own scripts, by the model through `browser_snapshot` or `browser_evaluate`, and by a prompt-injected page that steers the model to a login form; the plugin cannot tell a legitimate login page from a phishing one. The store is encrypted with the profile's `key4.db`, which sits in the same profile and is not bound to your Windows account (no primary password is set by default), so anyone who obtains the profile — a copy, a backup, `profile_isolation=copy`/`copy-keep`, or `scripts/profile-copy.mjs` — can decrypt the saved passwords; saved logins raise what a stolen profile is worth. Autofill on plain HTTP stays off (`signon.autofillForms.http` false), and address/credit-card autofill and form history stay off. **The plugin never reads, logs or transmits `logins.db` or `key4.db`**: `passwordManagerStore` is the file's existence only, and no credential value is ever printed. This setting does **not** change the [never-automate-the-credential-form rule](#sign-in): it only lets Firefox's own manager fill a credential you already chose to store; the model never types, submits, recovers or handles 2FA or CAPTCHA.

The pinned Camoufox build locks the manager off with its own enterprise policy (`PasswordManagerEnabled: false`, `OfferToSaveLogins: false` in `distribution/policies.json`), replaces the stock search-engine list with one dummy engine, and this Windows build has no readable per-user policy directory. The `camoufox` engine therefore **always runs on a plugin-owned overlay of the installed build** under Claude Code's plugin data directory at `<plugin data>/camoufox-overlay/<build directory>/` (see [Camoufox search engines](#camoufox-search-engines)): a real `distribution/` copied from the build with the search block replaced (and, with this setting on, the two password values set to true), every other policy preserved, a **junction** for every other top-level directory, a **hardlink** for every top-level file on the same volume (copies of the top-level files — about 310 MB — only when the plugin data and the Camoufox cache are on different volumes, guarded by a free-space check; never the whole 2.4 GB build), and an `overlay.json` marker. The launcher runs the overlay's `camoufox.exe` through `CAMOUFOX_EXECUTABLE_PATH` and the entry point strips a user `browser.camoufoxOptions.executable_path` from this session's plugin-data config copy (the user's file is never edited), so that key cannot silently bypass the overlay. The first overlay creation, and every build/policy/format change, is proved with one short headless browser start (the overlay temporarily carries a geolocation-permission policy; `denied` is the only success) and the final policy is written afterwards. Any failure — creation, junctions, free space, integrity, verification — runs the **stock build normally** and reports `blocked-by-overlay` with the reason; a `prompt` answer is cached for that build and policy, a timeout or error is retried on the next start, and a directory at the overlay path that this plugin did not write is never used, overwritten or removed (`blocked-by-existing-overlay`). The overlay is rebuilt when the build, its policy, the overlay format or the marker's manifest changes; the current and one previous build are kept; a tree a running browser still holds is left in place and reported. Turning the setting off removes the two password policies and the signon prefs on the next start; it never removes the overlay, because the search restore needs it. `browser_capabilities` and `browser_engine_status` report `passwordManagerEnabled`, `passwordManagerApplies`, `passwordManagerSource` (`overlay`, `prefs`, `stock`, `default`, `not-applicable`, `native-unavailable`, `blocked-by-overlay`, `blocked-by-existing-overlay`, `blocked-config`, `blocked-by-build-policy`), `passwordManagerPolicyFile` and `passwordManagerOverlay` (only when the overlay is in use), `passwordManagerOverlayMode` (`hardlink` or `copy`), `passwordManagerStore` (`firefox-logins-db-present` or `missing`, existence only) and a note. A build that no longer locks the manager off is used unchanged with the same signon prefs and reports `prefs`. Off is the default: no password key appears in any payload, no signon pref is merged and the build's password policy stays in force; the overlay itself is still created for the search restore.

## Accounts

One browser profile per account. Set **Account profile** to a name such as `alice`; the broker resolves it to a directory under Claude Code's plugin data directory and starts the engine with it. With Account profile, Profile directory, the default-profile pointer and Profile isolation at their defaults, nothing changes: the plugin uses `profiles/default` exactly as before.

| Account / setting | Effective profile directory |
|---|---|
| empty, isolation `shared` | `<plugin data>/profiles/default` |
| empty, isolation `workspace` | `<plugin data>/profiles/<engine>/ws-<sha256(cwd)[:7]>` |
| any, isolation `isolated` | **none** — no profile directory is created, locked or used |
| `default` | the engine's existing default profile — `profiles/default` for `cloak`/`playwright`, `profiles/<engine>/default` otherwise |
| `alice`, engine `cloak` | `<plugin data>/profiles/cloak/alice` |
| `alice`, engine `playwright` | `<plugin data>/profiles/playwright/alice` |
| `alice`, engine `camoufox` | `<plugin data>/profiles/camoufox/alice` |
| default pointer set, nothing else | the pointer's name: `default` means the engine default, any other name maps as an account |
| `profile_dir` set, isolation `shared`/`workspace` | that path, unchanged; Account profile, the default pointer and Profile isolation are ignored |

Precedence is **Profile isolation `isolated` → Profile directory → Account profile → Default profile pointer → Profile isolation `workspace` → engine default**. Only the first value that is set applies. `isolated` therefore overrides the profile settings instead of being overridden by them; the settings it made inert are reported (`profileIgnored`).

- **Names:** 1–64 characters, starting with a letter or digit, then letters, digits, `.`, `_` or `-`. No trailing dot, no slash, no Windows device name (`CON`, `NUL`, `COM1`, …). An invalid name is a start-up error: no browser starts and `browser_engine_status.lastError` carries the exact reason. The name is validated before any path is built, so it can never escape the profiles directory.
- **`camoufox-native` and `kameleo` do not use account profiles.** Their manifests declare `profileApplies: false`, so `browser_capabilities.profileApplies` and `accountApplies` are `false`; use `camoufox_profile` for the native engine, and Kameleo's own profile for the attach engine. Profile isolation and the lock preflight are inert for them too.
- **One account at a time.** The plugin configuration holds one value per key, so one plugin instance runs one account. Changing Account profile, Profile directory, Profile isolation or the proxy takes effect when the MCP server restarts — restart Claude Code. There is no runtime account switch. Two Claude Code windows share the same configuration and therefore the same account unless Profile isolation is `workspace` and they run in different project folders.
- **Visibility.** `browser_capabilities` reports `account`, `profileDir`, `profileSource` (`profile_dir`, `account`, `pointer`, `workspace`, `isolated`, `engine`, `default`), `defaultProfileDir`, `profileDefault`, `profileDefaultSource`, `profileDefaultPath` and, when the pointer is broken, `profileDefaultError`, plus `availableAccounts` (at most 100 names), `availableAccountCount`, `accountApplies`, `profileApplies`, `profileIsolation`, `profileIsolationSource`, `profileFallback` and `profileLock`. `browser_engine_status` adds `account`, `profileDir`, `profileIsolation`, `profileApplies`, `profileFallback` and `profileLock`. An **isolated** start adds `profileSource: "isolated"`, `profileDir: null`, `profileLock: null`, `profileIgnored` (the profile settings it ignored, with the value supplied), `profileIgnoredReason` and `profileIsolationNote`; `profileIsolationNote` says that the pointer and set-default do not affect this session. The `browser_profiles` meta-tool reports the same profile facts on demand and writes the pointer. The broker creates the account, pointer and workspace directories; it never copies, renames, moves or deletes a profile.
- **One profile per account, always.** Two identities in one profile overwrite each other's cookies and make the account history incoherent. Windows is case-insensitive, so `Alice` and `alice` are the same directory; the resolved path in `browser_capabilities` makes that visible.
- **Concurrency.** The bridge refuses a second server on the same profile directory (`Persistent profile is already active: <dir>`), and the CloakBrowser free tier allows **one concurrent browser session**. A second session is expected to fail at the engine; the plugin adds no account counter. A Pro licence is the supported path for concurrent sessions.
- See [Sign-in](#sign-in) for the manual, headed login each account needs.

### Default profile (applies at the next start)

The default-profile pointer is one line in `<plugin data>/profiles/<engine>/.default` that names the profile a start uses when **neither Profile directory nor Account profile is set**. It is the "always open my `work` profile unless I say otherwise" switch: set it once, and every future session starts on that profile without changing the plugin configuration. Precedence is in [Accounts](#accounts): Profile directory → Account profile → **default profile pointer** → Profile isolation → engine default.

- **Write it two ways.** Ask the agent to call the `browser_profiles` meta-tool with `action: "set-default"` and `name`, or run the script below before starting Claude Code. Both validate the name with the account rule and write the same file, atomically (a temporary file renamed over the pointer). A name of `default` maps to the engine default; any other name maps to the account-like `profiles/<engine>/<name>` and is created on the next launch.
- **It applies at the next server start — never to a running session.** There is no runtime profile switch: the broker resolves the profile once, before it starts the engine. `set-default` writes the pointer and says so; this session keeps its profile, and no browser is started, stopped or reconfigured.
- **A broken pointer is reported, never fatal.** A pointer that cannot be read, is not UTF-8, is empty, holds more than one line, or names something the account rule rejects is ignored for that start: the next source applies (the workspace profile when Profile isolation is `workspace`, otherwise the engine default), the reason goes to `browser_capabilities.profileDefaultError` and one MCP log line. The broker never falls back to a *different* profile silently.
- **Read it:** `browser_capabilities` reports `profileDefault` (the name, or `null`), `profileDefaultSource` (`pointer`, `none`, `invalid`, or `null` for an engine that does not use broker profiles), `profileDefaultPath` and `profileDefaultError`; `profileSource: "pointer"` means the pointer supplied this start's profile. `browser_profiles` (`action: "list"`, the default) reports the engine, the available profiles (existing directories plus the pointer's name, same 100-name cap), the current profile and its source, the pointer and its target directory, the effective profile directory and the current lock state. Both re-read the pointer at call time, so a `set-default` is visible in the report immediately even though it applies only at the next start. A running broker holds its own profile's lock, so `current.profileLock.state` is normally `live` with the backend's pid; that is this session, not a conflict.
- **Remove it:** close the browser, delete `<plugin data>/profiles/<engine>/.default`, and restart. The engine default (or the workspace profile) applies again. The plugin does not add a clear action; deleting the pointer is the documented way. Nothing under the profile directory is touched.
- The per-account `<name>.proxy` file works beside a pointer-named profile too: when the pointer names `work`, `profiles/<engine>/work.proxy` is used just like an account's file.

Run the script from a checkout of this repository at the repository root:

```powershell
node plugins/cloakbrowser/scripts/profile-default.mjs --show `
  --data-dir "$env:USERPROFILE\.claude\plugins\data\cloakbrowser-cloakbrowser-mcp"
node plugins/cloakbrowser/scripts/profile-default.mjs --set work `
  --data-dir "$env:USERPROFILE\.claude\plugins\data\cloakbrowser-cloakbrowser-mcp"
```

An installed plugin carries the same script at `<plugin root>/scripts/profile-default.mjs`, for example
`%USERPROFILE%\.claude\plugins\cache\cloakbrowser-mcp\cloakbrowser\<version>\scripts\profile-default.mjs`.

- `--show` is the default action: it reports the pointer path, whether it exists, the name, its state, the target directory and whether that target exists.
- `--set <name>` writes the pointer; `--dry-run` validates and reports without writing, and `--json` prints one machine-readable object. Exit codes: 0 read or written, 1 refused or failed, 2 usage error.
- `--engine <id>` defaults to `cloak`; `playwright` and `camoufox` are accepted too (any manifest with `profileApplies` true). `camoufox-native` and `kameleo` have no broker profile, so the tool refuses them.
- `--data-dir <path>` names the plugin data root. In a Claude Code process it is `CLAUDE_PLUGIN_DATA`; a terminal normally does not have that variable, so pass the directory explicitly. For this plugin it is `%USERPROFILE%\.claude\plugins\data\cloakbrowser-cloakbrowser-mcp`, which is `browser_capabilities.profileDir` two levels up. The fallback when nothing is set is `~/.cloakbrowser-mcp-plugin`, which is **not** where an installed plugin keeps its profiles.
- A pointer that names a profile that does not exist yet is valid: the next launch creates the directory, exactly like an account. The script never creates, copies, renames or deletes a profile.

### Per-account proxy file

A proxy can be sticky per account with a file beside the profile instead of the global **Proxy server** setting:

```
<plugin data>/profiles/cloak/alice.proxy        beside profiles/cloak/alice/
<plugin data>/profiles/default.proxy            beside profiles/default/
<plugin data>/profiles/camoufox/alice.proxy     beside profiles/camoufox/alice/
```

- **Proxy server set:** it wins, and one line in the MCP log says the file is ignored. **Proxy server empty:** the file is read for the active account, beside a pointer-named profile, or beside the default profile when no account and no pointer are set (only if the file exists). No file means a direct connection.
- The file is one line, no comments: `http://user:pass@host:port`, `https://…`, `socks4://…` or `socks5://…`. A missing scheme means `http://`. Percent-encode `@`, `:`, `/` inside credentials. The value is passed to the engine unchanged.
- A file that cannot be read, is not valid UTF-8, has more than one non-empty line, or does not parse as a proxy URL is a **start-up error**: the browser does not start and the error names the file, never its contents. A bad file never falls back to a silent direct connection.
- **The file is a credential in plaintext.** On POSIX run `chmod 600 <file>`; on Windows it inherits the user-profile ACL (the plugin does not change permissions). Keep it out of the repository, shared backups, PRs and screenshots; back it up like a password. The plugin only reads it, never writes it.
- The URL is never logged and never returned: `browser_capabilities` reports `proxySource` (`setting`, `account-file`, `none` or `error`) and `proxyConfigured` (boolean). Credential-bearing URLs in relayed backend log lines are masked as `scheme://***@host`.

### Backup, rename and delete (manual)

- **Backup:** close Claude Code (at least the browser), then copy the account directory and its `.proxy` file. A live Chromium profile contains lock files and can be copied in an inconsistent state. `.cloakbrowser-seed` sits inside the directory; keeping it keeps the fingerprint. For a checked copy that skips locks and caches, use the copy tool below.
- **Rename:** close the browser, rename the directory and the `.proxy` file, change Account profile (or Profile directory), and restart. Nothing is migrated for you.
- **Delete:** close the browser, delete the directory and the `.proxy` file. Irreversible. There is no delete in the plugin.
- To switch accounts: `/plugin` → Configure → set Account profile → restart Claude Code.

### Copy a profile (safe copies)

A copy branches an existing profile under a new account name with the same cookies, logins, local storage and fingerprint seed. Use it to experiment from a signed-in state, to keep a checked backup, or to start a second account from the same point. **A copy is not a new identity**: it presents the same fingerprint and the same sessions, so the one-account-per-profile rule still applies. It is not a way to move a session to a different account or to skip that account's sign-in.

1. **Close the browser first.** The profile lock exists while a browser uses the directory and a live Chromium profile is not safe to copy. The tool refuses a source whose bridge lock names a live process, and it also probes Chromium's own `<profile>/lockfile` with a write-open, so a browser started on the profile by another tool is refused too. A stale lock (owner gone) is ignored and is not copied. An unreadable lock also refuses the copy.
2. Run the copy tool, from a checkout of this repository at the repository root:

   ```powershell
   node plugins/cloakbrowser/scripts/profile-copy.mjs --from default --to work2 `
     --data-dir "$env:USERPROFILE\.claude\plugins\data\cloakbrowser-cloakbrowser-mcp"
   ```

   An installed plugin carries the same script at `<plugin root>/scripts/profile-copy.mjs`, for example
   `%USERPROFILE%\.claude\plugins\cache\cloakbrowser-mcp\cloakbrowser\<version>\scripts\profile-copy.mjs`.
   The tool uses the same account rule and the same `profiles/<engine>/<name>` layout as the broker:
   - `--data-dir <path>` names the plugin data root. In a Claude Code process it is `CLAUDE_PLUGIN_DATA`; a terminal normally does not have that variable, so pass the directory shown by `browser_capabilities.profileDir` two levels up — for this plugin `%USERPROFILE%\.claude\plugins\data\cloakbrowser-cloakbrowser-mcp`. The fallback when nothing is set is `~/.cloakbrowser-mcp-plugin`, which is why the command above passes it explicitly.
   - `--engine <id>` defaults to `cloak`; `playwright` and `camoufox` are accepted too (any manifest with `profileApplies` true). The resolved source path must agree with it: a profile under `profiles/<engine>/` for a different engine refuses the copy instead of guessing, so the wrong lock rule and exclusion list are never applied. Source `default` means `profiles/default` for `cloak` and `playwright`, and `profiles/<engine>/default` for `camoufox`.
   - `--dry-run` lists the top-level entries and totals without creating anything; `--json` prints one machine-readable summary.
   - `--from default --to work2` for engine `cloak` copies `profiles/default` to `profiles/cloak/work2`. A named source account lands at `profiles/<engine>/<name>`.
3. **Set Account profile to the copy** (`work2` above) and restart Claude Code. The copy starts signed in wherever the source was signed in.
4. **Copied:** cookies, logins, local storage, `Local State`, `Preferences`, the fingerprint seed `.cloakbrowser-seed`, and every `*.sqlite-wal` / `*.sqlite-shm` companion of a database. **Not copied:** the bridge profile lock, Chromium's own `lockfile`, Chromium singleton files (`SingletonLock`, `SingletonSocket`, `SingletonCookie`), caches (`Cache`, `Code Cache`, `GPUCache`, `GrShaderCache`, `GraphiteDawnCache`, `DawnCache`, `DawnGraphiteCache`, `DawnWebGPUCache`, `ShaderCache`, `Crashpad`), the `BrowserMetrics` dump, `*.tmp` entries and log directories. The browser rebuilds the caches on first use. The report names the engine-specific exclusions it removed. **A copy carries no session cookies**: Chromium deletes them at the next start, so only saved cookies are present.
5. **The optional `.proxy` file is not copied.** `profiles/cloak/work2.proxy` does not appear: the file is a plaintext credential, so the tool never duplicates it silently. Copy it yourself (and `chmod 600` it on POSIX) only if the copy should use the same proxy.
6. **Same identity, or a fresh one.** Because the seed is copied, the copy keeps the source fingerprint, which is what makes it useful. To give the copy a fresh fingerprint, close the browser and delete `<copy>/.cloakbrowser-seed` before the first start; the engine then writes a new seed. The copy tool never deletes or edits the seed for you.
7. **The free CloakBrowser tier still allows one browser at a time.** A copy adds no seat and no licence. Running two CloakBrowser sessions at once needs a Pro licence; `playwright` and `camoufox` are not Cloak-licensed.
8. **Refusals are complete:** an invalid name, a missing source, an existing destination (never overwritten, never merged), a live or unreadable bridge lock, and a live engine lock (`lockfile`). A failed copy removes only the destination directory it created, never the source and never a directory another process made.
9. **Session copies are pruned with the same tool.** `profile_isolation=copy` and `copy-keep` leave a temporary copy under `<plugin data>/profiles/<engine>/.sessions` while they run; `copy` deletes it on a clean shutdown, `copy-keep` moves it into the base path, and a crashed session keeps it in either mode. `node scripts/profile-copy.mjs --prune` lists those copies and removes the ones no live process owns (`--dry-run` and `--json` work as above; `--engine` selects the engine). It is the only pruning path, it is never automatic, and it never touches an account profile, the engine default or a retained `<base>.previous-<stamp>` tree from `copy-keep`.

## Session safety and profile isolation

A persistent Chromium profile can be used by only one browser at a time. The engine bridge takes an exclusive lock at backend start-up, before any browser or tool call, so a second Claude Code window that starts against the same profile cannot use that profile. Two windows can differ in project folder, account or scope and still collide, because `${CLAUDE_PLUGIN_DATA}` and the default profile are shared by every window.

Claude Code always starts one MCP server per window, and this plugin cannot change when the bridge locks. It can choose the profile, check the lock first, explain the result and, since 2.16.0, move the second window to its own profile instead of stopping it: **When the profile is in use** (`on_locked`, default `fallback`) starts it on a numbered sibling profile with a separate identity. That is what the session-safety release (2.8.0) added, and what `on_locked` extended.

### Profile isolation

**Profile isolation** (`profile_isolation`) has five values:

| Value | Profile for a window with no Account profile and no Profile directory | Behaviour |
|---|---|---|
| `shared` (default) | `<plugin data>/profiles/default` (or the engine default) | Exactly the previous behaviour, byte for byte. Two windows resolve the same identity; the second one is handled by **When the profile is in use** (`on_locked`): by default it starts on `profiles/default-2` with a separate identity, and under `block` the loud preflight below stops it |
| `workspace` | `<plugin data>/profiles/<engine>/ws-<sha256(cwd)[:7]>` | One identity per project folder, Playwright-style. Different projects never collide. The profile starts with a **fresh login state** — no cookies, logins or fingerprint seed from `profiles/default` are carried over |
| `isolated` | **none** | No browser profile at all. Nothing is created, locked or saved, every start is signed out, and nothing persists after the session. Account profile, Profile directory and the default-profile pointer are ignored and reported; several sessions can run at once |
| `copy` | the profile the ordinary precedence resolves, copied to `profiles/<engine>/.sessions/<base>-<YYYYMMDD-HHMMSS>-<pid>` | The browser runs on the **temporary copy**, not on the profile itself. The base keeps its exact bytes, is locked for the session so a shared/workspace window cannot use it, and the copy is deleted on a clean shutdown. It keeps the base's cookies, logins, local storage and fingerprint seed **as of the copy**; changes made during the session are discarded |
| `copy-keep` | the same base and the same session copy as `copy` | Same start, preflights, base lock and copy. On a **clean** close the base is renamed to `<base>.previous-<YYYYMMDD-HHMMSS>` (retained) and the session copy takes the base path, so the session's changes are kept. The retained tree is listed by `browser_profiles` under `previousTrees` and never removed by the plugin or by `--prune`. A hard kill performs **no swap**: the base stays byte-identical and the session tree is retained. Refused when the base is outside the plugin data directory |

- The hash is Playwright's own derivation: SHA-256 of the exact working-directory string, first seven hex characters. For example `D:\Projects2\StealthBrowserAutomation` → `ws-0b0e194`. The same folder always maps to the same profile; a different spelling of the same path (different case or separator) maps to a different one.
- Precedence: **isolated → Profile directory → Account profile → default-profile pointer → Profile isolation `workspace` → engine default**. An explicit Profile directory or Account profile therefore keeps its exact previous meaning in `shared`, `workspace`, `copy` and `copy-keep`, and `shared` never changes an existing path. `isolated` is the exception: it uses no profile, so the other profile settings cannot apply, and the broker reports each one it ignored as `profileIgnored` with the supplied value. `copy` and `copy-keep` resolve the base with the same precedence as `shared` and **do not combine with `workspace`**: with no Profile directory, Account profile or pointer they copy the engine default, never a workspace profile. To get a per-project copy, set Profile directory to that project's own path and use `copy` (or `copy-keep`).
- **Isolated** starts the engine with its own isolated switch (`PLAYWRIGHT_MCP_ISOLATED=true`) and no user-data-dir: the Cloak bridge passes the switch through when it sets no profile and the pinned Playwright MCP launches the browser without a persistent context, and the Camoufox wrapper reads the same variable. The browser may use a temporary directory for its lifetime; the plugin creates **no** profile directory and nothing survives the session. The fingerprint seed is not carried, so the same account looks like a fresh browser each start. Sessions do not take the profile lock, so several Claude Code windows can run against the same account at once — the CloakBrowser seat limit still applies.
- **Persistent, not "in memory".** The wording is deliberate: the engines keep their browser profile ephemeral, but the guarantee this plugin makes is that nothing persists and no profile directory is created, not that the browser process holds everything in RAM.
- The free CloakBrowser licence still allows **one browser at a time**. `workspace` and `isolated` remove the profile collision, not the seat limit: with two browsers running, the second fails at the engine with the licence error, not with the profile lock. The stock `playwright` and `camoufox` engines are not Cloak-licensed and do not have that seat cap.
- A workspace profile is an ordinary profile directory: it keeps its own `.proxy` file beside it (`<plugin data>/profiles/<engine>/ws-<hash>.proxy`) and survives restarts and updates. Nothing is moved, copied or deleted. An isolated start has no profile, so no account `.proxy` file is read; the `proxy_server` setting still applies because a proxy is not profile state.

### Copy sessions

`profile_isolation=copy` runs the browser on a temporary copy of the resolved profile and never writes to the profile itself. At start the broker:

1. resolves the base exactly as `shared` would (`profile_dir` → `account` → the default-profile pointer → engine default; never a workspace profile);
2. runs the bridge-lock and engine-lock preflights on the base. When the base is live: under `on_locked=block` it **refuses loudly** — the meta-tools answer, no copy is made, and there is no fallback to another profile; under the default `on_locked=fallback` the sibling becomes the base and is copied instead (never the live profile); under `on_locked=isolated` this start has no profile at all and makes no copy;
3. takes the base's lock in the bridge's own format (`<base>/.cloakbrowser-mcp-profile.lock`, `{pid, createdAt, userDataDir}`), so a second shared/workspace window on the same profile is refused for the session and the bridge itself would refuse it too; a stale lock is reclaimed by PID liveness under the bridge's own identity rule;
4. copies the base through the same exclusion engine as `scripts/profile-copy.mjs` into `<plugin data>/profiles/<engine>/.sessions/<base>-<YYYYMMDD-HHMMSS>-<pid>`: cookies, logins, `Local State`, `Preferences`, `IndexedDB`/`localStorage` files, the fingerprint seed and every `*.sqlite-wal`/`*.sqlite-shm` are kept; locks, singleton files, caches, `BrowserMetrics`, thumbnails, `*.tmp` and log directories are not;
5. starts the engine with the session copy as its user-data-dir. The base is not writable by the session, and the copy keeps the base's fingerprint seed unchanged (the same identity, as of the copy).

On a **clean** shutdown (Claude Code closes the MCP server, or the broker gets SIGINT/SIGTERM/SIGHUP) the broker stops the backend, deletes the session tree and releases the base lock; one log line says the copy was discarded. On a **hard kill** (SIGKILL, `taskkill /F`) the copy is kept — data is never lost — and the base lock is left as a stale file whose dead PID every preflight reclaims. The next session sees the leftover copy in `browser_profiles` `sessionCopies` (state `leftover`; a copy whose browser still runs is `active`, and the current one is `current`), with its path and start time, and removes it explicitly:

```
node scripts/profile-copy.mjs --prune --engine cloak --data-dir <plugin data>
node scripts/profile-copy.mjs --prune --dry-run --json ...
```

`--prune` removes only copies no live process owns; it never touches an account profile or the engine default, and the plugin never prunes automatically. A copy session reads the base's `.proxy` file (it is configuration, not identity) but the copy tool never duplicates it; `proxy_server` still wins. `camoufox-native` and `kameleo` manage their own profiles, so `copy` is refused loudly for them instead of starting them another way.

### Copy-keep sessions

`profile_isolation=copy-keep` is the same session as `copy` — same base resolution, same preflights, same base lock, same `.sessions` copy and exclusions — plus one rule: **the last clean session wins**. On a clean close, after the backend has exited, the broker:

1. waits **bounded** (5 s, polling every 100 ms, never forced) for the session copy's own locks — the bridge lock and the engine's `lockfile` — to be released;
2. renames the base to `<base>.previous-<YYYYMMDD-HHMMSS>` beside it (a same-second collision gets `-2`, `-3`, …), retrying a transiently refused rename (Windows `EPERM`/`EBUSY` while a dying browser or an indexer still holds a handle) for up to 3 s;
3. renames the session copy into the base path;
4. only then removes the session-owner marker from the new base and releases the base lock, which travelled into the retained tree with the old base.

The result is reported: the broker that swaps is exiting, so it writes a small `<plugin data>/profiles/<engine>/.last-swap.json` record (`state`, base, session copy, previous tree, restore flag, error) and the next `browser_profiles` call reports it as `lastSwap`; the retained trees appear under `previousTrees` (bounded, newest first). `browser_capabilities` and `browser_engine_status` report them too when a record or a tree exists.

- **The previous tree is user data.** It is never deleted by the plugin and never removed by `scripts/profile-copy.mjs --prune`, which still only touches leftover `.sessions` copies. The trees accumulate (each is one profile tree, minus caches) until you delete them yourself; `previousTrees` makes the cost visible.
- **A hard kill performs no swap.** The base keeps its exact bytes, the session tree is retained and listed as a leftover `.sessions` copy, and the base lock is a stale file whose dead PID the next preflight reclaims.
- **A failed swap loses nothing.** If the first rename fails the base is untouched. If the second fails, the base is renamed back from the previous tree, the session copy is kept, and the failure names both paths. If the previous tree cannot be restored either, both paths are reported and the old base remains at the previous-tree path.
- **Refused outside the plugin data directory.** A whole-tree swap on an arbitrary real profile is not something the plugin will do: when Profile directory resolves outside the plugin data directory, `copy-keep` refuses loudly and names the fix, while `copy` stays allowed because it never writes the base. `camoufox-native` and `kameleo` are refused exactly as in `copy`.
- **Everything a copy carries is carried, and the fingerprint seed is unchanged** (the new base is the session copy, so it is the same identity as of the copy).

### Loud preflight

Before spawning the backend, the broker reads the bridge's own lock file, `<profile>/.cloakbrowser-mcp-profile.lock`. When a **live** process owns it, the outcome depends on **When the profile is in use** (`on_locked`): under `block` (and always for an explicit Profile directory) the broker does not start a doomed backend — the meta-tools answer instead, and the same sentence appears in `initialize.instructions`, `browser_capabilities.engineError` and `browser_engine_status.lastError`:

```
The browser profile <dir> is already in use by pid 25028, started 2026-10-24T14:09:50.197Z.
Close the Claude Code session or browser window that owns this profile (pid 25028, started ...);
if that process is gone, the lock is reclaimed automatically. You can also set "Profile directory"
(profile_dir) to another folder, or set "Profile isolation" (profile_isolation) to workspace so each
project folder gets its own profile. Restart Claude Code after the change. The backend was not started.
```

- `browser_capabilities.profileLock` and `browser_engine_status.profileLock` report `{ state, profileDir, path, owner: { pid, createdAt }, fix }`. `state` is `free` (no lock), `live` (owner exists, start refused), `stale` (owner is gone; the bridge reclaims it automatically) or `invalid` (the file exists but cannot be read; the start is refused and the fix names the file).
- The `cloak` and `playwright` engines also declare Chromium's own `<profile>/lockfile`, reported as the additive `engineProfileLock` key (`{ state, profileDir, path, file, liveness, owner, error, fix }`). `liveness` is `exclusive-open-write`: the broker opens the file `r+`, closes it at once and never writes, because Chromium allows a plain read while it runs but refuses a write-open. `state` is `free`, `live` (another process holds it: the same loud meta-only start, naming the profile, the lock file and the fix), `stale` (a leftover file nobody holds, which does not block) or `unknown` (reported with the reason and ignored). Only `live` blocks a start.
- A lock whose recorded process is gone is **not** removed by the plugin. It is reported as `stale`, and the bridge reclaims it at start-up exactly as before.
- A lock file that exists but cannot be read also stops the start: the bridge cannot reclaim it either, so the plugin names it instead of letting the backend exit.
- The preflight is best-effort: it narrows the window, but the bridge remains the authority. If another process takes the lock between the check and the bridge start, the bridge's own message now reaches `browser_engine_status.lastError` as well, because the last launcher/backend stderr line is reported for **every** engine.
- Proxy URLs are never printed: the lock text contains no proxy, and relayed stderr is redacted as before.

### When the profile is in use

**When the profile is in use** (`on_locked`, default `fallback`) decides what a start does when the profile it resolved is held by a live owner. It is the second half of session safety: the preflight above finds the owner, and this setting chooses between stopping, waiting and starting with no profile.

**The cloak engine declares one concurrent browser seat** (`singleSeat` in its manifest): the free CloakBrowser licence allows one running browser, so a second profile would only fail at the first browser action. A busy profile is therefore **held**, never duplicated:

| `on_locked` | A busy profile on `cloak` (one seat) | A busy profile on `playwright` / `camoufox` (no seat) |
|---|---|---|
| `block` | The 2.15 behaviour: no backend, meta-tools only, owner and fix named | Same |
| `fallback` (default) | **Hold and retry**: no backend, the cached tool list stays, every tool call retries and recovers | The first free numbered sibling `<name>-2` … `<name>-5` (bridge lock **and** engine lock free) |
| `isolated` | A start with no profile at all | Same |

Reporting, per path:

- **Hold** (`fallback` on `cloak`): `onLocked: "fallback"`, `profileFallback: null` and `hold: { state: "waiting" | "recovered" | "failed", profileDir, owner, attempts, recoveredAt?, toolList: { source, savedAt }, error? }` in `browser_capabilities`, `browser_engine_status` and `browser_profiles` (`current`); `backendState: "waiting-for-profile"` while it waits; one sentence in `initialize.instructions` that says it retries and no restart is needed; one MCP log line per attempt. While the profile is busy a tool call returns an `isError` naming the owner. When the profile frees, the next tool call starts the backend, replays the client's handshake to it, answers that call and sends `notifications/tools/list_changed` so the client re-lists the real surface.
- **Cached tool list**: after every successful `tools/list` the broker writes the backend's own tool objects to `<plugin data>/cache/<engine>/tools-<profile>-<digest>.json` (the digest covers the seven tool-group switches, the MCP package pin and the broker version). A held session serves that list through the normal manifest → profile → `disabled_tools` filter, so its tools stay visible and callable-shaped; the list is never served stale, because the filter runs on read. A cold first-ever start has no cache and says so: only the broker meta-tools answer until the profile frees.
- **Sibling** (`fallback` on `playwright`/`camoufox`): `profileFallback: { from, to, reason }`, the same sentence in `initialize.instructions`, and the sentence names the profile. That profile is a **different identity**: separate cookies, logins and fingerprint seed. It keeps the base's `.proxy` file (a proxy is configuration, not identity). In the copy modes the sibling becomes the base: `copy` copies it and `copy-keep` swaps the session copy into it on a clean close; the live base is never copied or replaced.
- **Isolated**: `profileSource: "isolated"`, `profileDir: null`, `profileFallback: { from, to: null, reason }`, its own `profileIsolationNote` and the ignored settings; `profile_isolation` itself is reported unchanged. On `cloak` an isolated second browser still hits the licence at launch, and the engine's own message names it.
- An explicit **Profile directory** is never duplicated on the sibling path (`<path>-2` is not created). On a one-seat engine it is **held** like any other busy profile, because a hold creates and moves nothing.
- Unset, empty, a placeholder or an unknown value all mean `fallback`; an unknown value is logged once.
- `camoufox-native` and `kameleo` manage their own profiles: the setting has no effect there and their payloads gain no `onLocked` key.

#### The workspace rule

With `profile_isolation=workspace` on an engine **without** a seat limit, when the derived workspace profile is locked by a live owner the broker tries the numbered siblings `ws-<hash>-2` … `ws-<hash>-5`. The first one whose bridge lock is absent, stale or unreadable-by-the-bridge is used, and the switch is always reported (`profileFallback` in both meta-tools, the same sentence in `initialize.instructions`, one log line):

```
The workspace profile <data>/profiles/playwright/ws-0b0e194 was already in use (pid 25028, started ...),
so this session uses <data>/profiles/playwright/ws-0b0e194-2 instead. It has separate cookies, logins
and fingerprint seed.
```

This rule predates `on_locked`, and its sentence and selection rule are byte-identical to 2.15. On a **one-seat engine** it is not used at all: a workspace sibling is a second browser the licence refuses, so `block` stops the start and `fallback` holds it.

- When `ws-<hash>-2` through `ws-<hash>-5` are all live-locked, no backend starts and the error says so, naming the base owner.
- Fallback applies only to the profile derived by `profile_isolation=workspace`. An explicit Account profile or Profile directory is never moved aside by the workspace rule.

### Concurrent windows, plainly

| Situation | `shared` (default) | `workspace` |
|---|---|---|
| Two windows, different project folders | Second window: `fallback` **holds** (cloak) or uses a sibling (playwright/camoufox); `block` shows the loud preflight | Both resolve their own profile; the second still holds on cloak, because one seat is one seat |
| Two windows, same project folder | Same as above | Same |
| Two windows, same named Account profile | Same as above | Same |
| Same profile, one window closed | The held window recovers on its next tool call; a stale lock is reclaimed by the next start | Same |

To run two CloakBrowser browsers at once you need a Pro licence; no profile setting adds a seat. `workspace` is for isolating projects, not for lifting that limit.

## Engines and the broker

`broker.mjs` is the single MCP server Claude Code starts. It reads the **Browser engine** setting, discovers every `engines/*.json` manifest, validates it, loads the selected one, starts `launch.mjs` for that engine and relays JSON-RPC in both directions. The engine value is an enum in the plugin configuration, never a command or a path. The enum (`browser_engine.options`) is generated from the manifests; adding an engine does not edit the broker. See `engines/README.md` for the add-an-engine recipe.

| Engine | Manifest | Backend | Notes |
|---|---|---|---|
| `cloak` (default) | `engines/cloak.json` | CloakBrowser Chromium on Patchright | Stealth patches; the 1.x browser behaviour is unchanged |
| `playwright` | `engines/playwright.json` | Stock Playwright Chromium | Same Playwright MCP contract, no stealth patches |
| `camoufox` | `engines/camoufox.json` | Camoufox stealth Firefox via `camoufox-playwright-mcp` 0.1.5 | Provisions uv, Python and its venv automatically; portable by default; four tools absent and `browser_pdf_save` unusable; no CDP |
| `camoufox-native` | `engines/camoufox-native.json` | Camoufox stealth Firefox via PyPI `mcp-camoufox` 0.4.5, fetched into a plugin-managed venv | Its own 27-tool contract; 16 canonical aliases + 9 prefixed native tools; portable by default; 10 portable verbs absent; no CDP; licence FSL-1.1-MIT; never bundled |
| `kameleo` | `engines/kameleo.json` | A running Kameleo Chroma profile over CDP | Full 72-tool contract over attach; portable by default (27), 75 at full; the profile and its proxy belong to Kameleo; Junglefox unsupported; no local diagnostics; **stealth UNVERIFIED**, no detector run |

Every manifest is the source of truth for whether the profile model applies: `cloak`, `playwright` and `camoufox` own a local profile directory and resolve `profile_dir`, `account` and `profile_isolation` — including `isolated`, which starts them with their own isolated switch (`PLAYWRIGHT_MCP_ISOLATED=true`) and no profile (`profileApplies: true`, the default). `camoufox-native` (the app owns its profile and its lease) and `kameleo` (CDP attach) declare `profileApplies: false`; for them the profile settings, the lock preflight, the workspace derivation and `isolated` are inert, and the meta-tools report `profileApplies: false` (plus, in an isolated start, `profileIsolationNote` saying the setting has no effect on that engine). The broker has no engine-id branch for this rule.

The Camoufox engine differs from the Chromium engines where the backend does:

- **Tools it does not implement:** `browser_annotate`, `browser_emulate_media`, `browser_start_recording` and `browser_stop_recording` are hidden (`support: none`), and `browser_pdf_save` is hidden because PDF output only works on headless Chromium. They are reported in `browser_capabilities.unavailableTools` with a reason.
- **`browser_run_code_unsafe` is `partial`:** it executes asynchronous **Python** Playwright code against the active page, not JavaScript. It is hidden under `portable` (not on the shared list) and exposed with its note under `full`.
- **Ignored settings:** `humanize`, `human_preset`, `release_channel`, `geoip_proxy_match`, `licence_key` and `engine_version` do not apply to Camoufox and are listed in `browser_capabilities.ignoredSettings`. `headless`, `profile_dir`, `proxy_server`, `proxy_bypass`, `output_dir`, `identity_mode` and the seven tool groups do apply. The default profile root for this engine is `<plugin data>/profiles/camoufox/default`; do not point it at a Chromium engine's profile directory.
- **Device identity:** **Device identity (Camoufox)** (`identity_mode`, default `profile`) stores one generated fingerprint in `<profile>/.camoufox-identity.json` on a profile's first launch and passes it to the wrapper on every later launch through a per-profile `CAMOUFOX_MCP_CONFIG` file under the plugin data directory, so a persistent profile keeps the same device (user agent, platform, screen, GPU, fonts, voices, media devices and audio seed) while its cookies persist; `random` restores the per-launch draw, and an isolated start has no profile so it always draws a new one. The file travels with `copy`/`copy-keep`; delete it to rotate; a corrupt file is removed, regenerated and reported. `browser_capabilities`/`browser_engine_status` report `identityMode`, `identityApplies`, `identitySource`, `identityFile`, `identityCreatedAt` and, when relevant, `identityNote`. The other engines ignore the setting and say so: `cloak` pins its own Chromium seed, `playwright` has no identity input, and Kameleo owns its profiles. The rule is reported from the broker and cannot be a manifest field: an engine manifest feeds its venv marker, so editing one would rebuild every user's venv.

### Camoufox search engines

The pinned Camoufox build ships an enterprise policy that removes the stock search engines, points the address bar at a policy-only dummy engine called `None` and adds that dummy itself, so a stock install cannot search at all. This build also hard-disables its own engine configuration (`SearchEngineSelector` in `browser/omni.ja` returns one inert `None` engine instead of reading the packaged `search-config-v2`, and `services.settings.server` is empty). Since 2.17.0 the `camoufox` engine **always runs on a plugin-owned overlay build** whose `distribution/policies.json` replaces that one block with

```json
"SearchEngines": {
  "Default": "Google",
  "PreventInstalls": false,
  "Add": [ Google, DuckDuckGo, Bing, Wikipedia (en), Perplexity ]
}
```

and preserves every other policy byte for byte. The five engines are the ones the build's packaged configuration defines for its default `en-US` environment, written with their public search URLs; the policy list is the only offline route this build supports, nothing is fetched from Mozilla's servers, and no partner/telemetry codes are invented. Google is the default once — a one-time seed per policy value, not a lock: the default dropdown, the engine list, the enable/disable toggles, “Restore Default Search Engines” and the add-engine flow all stay usable, and a change you make in `about:preferences#search` persists. A profile created under the old policy has its `search.json.mozlz4` renamed once to `search.json.mozlz4.backup-<timestamp>` beside it (never deleted) and a per-profile `.camoufox-search-migration.json` marker written, so Firefox rebuilds the list; a failed rename keeps the file, starts normally and is reported. `browser_capabilities` and `browser_engine_status` add `searchEnginesSource` (`overlay`, `stock`, `blocked-by-overlay`), `searchEnginesDefault`, `searchEnginesPolicyFile` and `searchEnginesNote` for this engine only. The overlay is not optional and has no setting; if it cannot be created or verified, the stock build runs with its own policy in force and `searchEnginesSource` reports `blocked-by-overlay` with the reason. The plugin never navigates to a search URL and sends no query: suggestions stay off by default and a query leaves only when you submit one, to the engine you chose. See [Saved logins and autofill](#saved-logins-and-autofill) for the same overlay's password side.

### Camoufox native aliases

`camoufox-native` does not speak the Playwright contract, so the broker translates the honest subset and prefixes the rest. Everything is declared in `engines/camoufox-native.json`; there is no engine-specific code in the broker.

- **16 canonical aliases:** `navigate`, `go_back`, `snapshot`, `click`, `fill` (twice: `browser_type` and `browser_select_option`), `fill_form`, `press_key`, `find`, `evaluate`, `screenshot`, the four tab tools behind `browser_tabs`, `list_network_requests`, `list_console_messages`, `handle_dialog` and `close_session` appear as their `browser_*` names with a canonical (projected) input schema. Arguments the native tool cannot honour are rejected at call time and are not advertised: for example `browser_click` has no `button` or `modifiers`, `browser_type` has no `slowly` or `submit`, `browser_take_screenshot` has no `type`, `filename` or `scale`, and `browser_snapshot` accepts no canonical arguments.
- **9 prefixed native tools:** `camoufox_native_get_element`, `camoufox_native_get_html`, `camoufox_native_get_network_request`, `camoufox_native_scroll`, `camoufox_native_upload_file`, `camoufox_native_wait_for`, `camoufox_native_click_at`, `camoufox_native_reload` and `camoufox_native_list_sessions`. They keep their native names, descriptions and schemas.
- **10 absent portable verbs:** `browser_hover`, `browser_drag`, `browser_file_upload`, `browser_wait_for`, `browser_network_request` and the five `browser_cookie_*` tools are `none` with a reason in `browser_capabilities.unavailableTools`. There is no hover or drag tool; file upload, wait conditions and request addressing have different native semantics and stay prefixed; there are no cookie tools at all.
- **The profile is injected by the broker.** Every native call except `list_sessions` receives the configured `camoufox_profile`; the agent never sees the argument.
- **Results are native.** Snapshot text, tab listings and network numbering are mcp-camoufox's formats, not Playwright's. The broker passes results through untouched and does not pretend they are identical.
- **The seven tool-group switches do not apply.** They shape the Playwright MCP capability groups inside the cloak launcher. For this engine, `tool_profile` and `disabled_tools` are the controls; `browser_capabilities.groupSwitchesApply` is `false`.
- **No identity input.** `mcp-camoufox` 0.4.5 passes no fingerprint or seed option, so **Device identity (Camoufox)** (`identity_mode`) is inert for `camoufox-native` and each browser start draws a new device identity; `browser_capabilities.identitySource` is `"native-unavailable"` and `identityNote` says so.
- **No saved-login input.** `mcp-camoufox` 0.4.5 has no arbitrary Firefox prefs input, so **Saved logins and autofill (Camoufox)** (`password_manager`) is inert for `camoufox-native`; `browser_capabilities.passwordManagerSource` is `"native-unavailable"` and `passwordManagerNote` says so.
- **No file-path tools.** `mcp-camoufox` returns screenshot image data and uploads by element, so this engine has no file allowlist and never reads `PLAYWRIGHT_MCP_ALLOW_UNRESTRICTED_FILE_ACCESS`. `browser_capabilities.ignoredSettings` lists `allow_unrestricted_file_access` for it.
- **Detection note (2026-10-24).** Six headed runs through the broker on `https://deviceandbrowserinfo.com/are_you_a_bot` were recorded, and the flag is **persona-driven**, not cold-start:
  - With a random persona that picked macOS/MacIntel on this Windows host, `isBot: true` both times, caused solely by `hasInconsistentTimingResolution: true`; every other signal was false, including `isAutomatedWithCDP`, `isAutomatedWithCDPInWebWorker` and the WebGL checks.
  - With `CAMOUFOX_FINGERPRINT_OS=windows` (cold and warm, same fresh profile), `isBot: false` both times with every flag false.
  - With the new host-OS default and a fresh profile (`os=windows` in the launcher log), `isBot: false`, `hasInconsistentTimingResolution: false`, `isAutomatedWithCDP: false`, navigate 7.9 s.
  - With `CAMOUFOX_FINGERPRINT_OS=macos`, the page returned no verdict within the probe window (inconclusive).
  - No fingerprint-scan redirect occurred; the URL stayed on the detector page.
  - **Conclusion:** the native engine now defaults the persona to the host OS for coherence, which produced a clean run here. This is not a general stealth validation: a macOS host would default to `macos` (not tested here), and `CAMOUFOX_FINGERPRINT_OS` is not a plugin setting — set it in the environment to override.

### Kameleo engine

`kameleo` is the attach engine: the browser already exists as a Kameleo profile, and the plugin drives it through Kameleo's local CDP WebSocket. Everything is declared in `engines/kameleo.json` and `launch-kameleo.mjs`; there is no engine-specific code in the broker, which reads the manifest's `requiredEnv`, `runtime`, `capabilities` and `systemDependencies` blocks generically.

- **Setup (the plugin never installs Kameleo).** Kameleo is a commercial desktop application, so it is a detected prerequisite, not a provisioned dependency. There is no package-manager path (no `winget` on the build machine) and the plugin never downloads, runs or starts the installer:
  1. Download `Kameleo.Installer.exe` (about 150 MB) from <https://kameleo.io/downloads>; the vendor lists Windows 10 or newer.
  2. Run the installer, start Kameleo, sign in and activate the licence.
  3. Create or select a **Chromium (Chroma)** profile (Junglefox is Firefox and cannot be attached). Start the profile or let Kameleo start it when the endpoint is opened.
  4. Copy the profile ID from the profile row into **Kameleo profile ID**, select the `kameleo` engine, and restart Claude Code.

  The vendor's download page stated on 2026-10-24 that no account is needed and that a free tier exists; that is **vendor-reported and was not tested here**.
- **Dependency reporting.** `browser_capabilities.systemDependencies` lists the app with `status: "unknown"` until there is evidence, then `"missing"` with the install hint after a configuration error, a backend failure or a failed tool call. The same hint is appended to `browser_engine_status.lastError` and to the synthesized `initialize` instructions. The declared fields are `id`, `label`, `required`, `downloadUrl`, `installerName`, `installHint` and `licenceNote`; the broker never acts on them.
- **Endpoint.** The default is `ws://127.0.0.1:5050/playwright/<profile ID>`, with the ID percent-encoded as one path segment. An explicit **Kameleo CDP endpoint** overrides it, with the loopback-only validation described under Requirements.
- **Missing profile ID.** This is a configuration error before any process starts: `initialize` explains it, only the three meta-tools are exposed, `browser_engine_status.backendState` is `failed`, and `browser_engine_status.lastError` / `browser_capabilities.engineError` carry the exact sentence that names `kameleo_profile_id`.
- **App not running or port closed.** `initialize` and `tools/list` still answer, because the CLI is lazy. The first browser call fails with `isError: true`; the broker appends the Kameleo prerequisite sentence. After the first successful tool call, errors pass through unchanged. This enrichment is declared by the manifest (`runtime.errorHint`) and exists only for engines that declare it; every other engine's relay is byte-identical.
- **Tool support.** `*` is `full`; `browser_close` and the two tracing tools are `partial`; `browser_start_video`, `browser_stop_video`, the three video helpers, `browser_start_recording`, `browser_stop_recording` and `browser_annotate` are `unknown` (exposed, with a reason, and a call may fail). No tool is `none`: the backend is the full official 72-tool Playwright MCP contract.
- **Group switches apply.** Unlike `camoufox-native`, this engine runs the official Playwright MCP CLI, so the seven `tools_*` switches shape `PLAYWRIGHT_MCP_CAPS` exactly as they do for `cloak`. `browser_capabilities.groupSwitchesApply` is `true`, and `browser_capabilities.cdpAttach` is `true`.
- **Diagnostics.** `browser_engine_status` gains `kameleoEndpoint` and `kameleoProfileId` for this engine only. The names come from the manifest's `runtime.statusKeys`; they are absent for every other engine.
- **No bridge, no local diagnostics.** The launcher starts the pinned `@playwright/mcp` CLI directly, so `cloakbrowser_binary_info` and `cloakbrowser_bridge_info` do not exist here and the full surface is 75, not 77. The seven tool groups, `tool_profile`, `disabled_tools` and `output_dir` still apply.
- **Stealth status: UNVERIFIED.** Kameleo is not installed on the build machine and nothing listens on 5050, so no attach and no detector run were performed. Patchright's documented benefit is on its own launch path; whether it suppresses CDP tells when the client attaches to Kameleo's Chromium is **unknown**. Kameleo also advises against adding third-party stealth patches, so the combination is untested in both directions. Do not read this engine as stealth-validated until a recorded detector run exists.

### Tool profiles

Every manifest declares a default profile and per-tool support (`full`, `partial`, `none`, `unknown`). The **Tool profile** setting (`default`, `portable`, `full`) overrides the manifest default; `default` means "use the manifest's choice". `full` exposes everything the manifest does not mark `none`. `portable` exposes one shared 24-tool browser core, defined once in `engines/profiles.json`:

| Engine | Default | `full` | `portable` |
|---|---|---:|---:|
| `cloak` | `full` | 77 | 27 |
| `playwright` | `full` | 77 | 27 |
| `camoufox` | `portable` | 70 | 27 |
| `camoufox-native` | `portable` | 28 | 17 (of which 3 meta) |
| `kameleo` | `portable` | 75 | 27 (of which 3 meta) |

The `camoufox-native` counts include the three broker meta-tools: 25 exposed tools at `full` (16 canonical + 9 prefixed) and 14 canonical tools at `portable` — ten portable verbs are not available on that engine. The group switches do not apply to it. The `kameleo` counts also include the three meta-tools: 72 browser tools at `full` and 24 at `portable`; the group switches do apply, so with fewer groups both counts fall. With all seven groups off, `kameleo` exposes 28 at `full` (25 browser + 3 meta) and 22 at `portable` (19 + 3): the CLI's minimal 25-tool set contains 19 of the 24 portable names, including `browser_close`.

The broker adds three meta-tools that are always present and cannot collide with backend tools:

| Meta-tool | What it reports |
|---|---|
| `browser_capabilities` | Selected engine, label, contract, effective `toolProfile` and its source, per-tool support and notes, the portable list, what the profile and manifest hid, how to change engines, the profile facts (`profileIsolation`, `profileApplies`, `profileFallback`, `profileLock`, `engineProfileLock` when the engine declares its own lock file, `profileDefault`, `profileDefaultSource`, `profileDefaultPath`, `profileDefaultError`), and the artifact facts: `serverCwd`, `outputDir`, `clientRoots` and, when the roots could not be read, `clientRootsError` |

The `browser_capabilities` and `browser_engine_status` descriptions mention the profile diagnostic, so an agent that sees only the three-tool degraded surface knows to call them when a profile is already in use. `browser_profiles` is always present too, including that degraded start, so the default can still be read or set when a backend is unavailable.

## Sign-in

Sign in to Google or any site manually, in the headed window, with the persistent profile. Automate only the logged-in session. **Never automate the Google credential form** — or any site's password, recovery, 2FA, passkey or CAPTCHA step.

Per account:

1. Set **Account profile** to the account name and restart Claude Code.
2. Ask the agent to open the site's sign-in page in the headed window (`headless` stays off).
3. The agent stops at the credential form and says it is waiting.
4. Type the email, password and any 2FA or CAPTCHA in that window yourself and finish the login.
5. The agent confirms the signed-in state by reading the page (name or avatar), never by reading secrets.
6. The session is stored in that account's profile directory and reused on the next start.

Never automated, for any account or engine: the credential form, password entry, account recovery, 2FA or passkey prompts, CAPTCHA or bot challenges; account creation; copying cookies, storage state or a profile between accounts to skip a login. Log in through the same proxy and approximate location the account normally uses — a sudden geo change is an anomaly signal to the platform. One account per profile, always.

| Preset | Switches on | Browser tools |
|---|---|---:|

Those counts are backend `browser_*` tools. The two local diagnostics and the three broker meta-tools are additional and are not controlled by these switches.

```
browser_pdf_save,browser_start_video,browser_mouse_wheel
```

Changes take effect after the MCP server restarts.

- The MCP package does **not** self-update. Update by changing the pin in `.mcp.json` (`CLOAK_PLAYWRIGHT_MCP_PACKAGE`) and `plugin.json` together; the launcher reinstalls into the plugin data directory when either pin changes.
- The Chromium binary **does** self-update: on each launch the wrapper checks at most once per hour and downloads a newer build in the background.
